# Ключевые особенности KarpikEngine

Этот документ описывает особенности движка, важные при разработке и публикации игры: модульную сборку, SDK для игровых проектов, подготовку ресурсов, регистрацию сервисов и настройку журналирования. Это не перечень всех игровых подсистем.

## Модульная сборка игры

Движок собран из модулей. Модуль может содержать сервисы, игровые системы и зависимости от других модулей. Клиентская, серверная и общая части игры выбирают свои наборы модулей; несовместимые зависимости между сторонами обнаруживаются при сборке.

Для игры задаётся профиль модулей: какие модули включены и, если у модуля есть варианты реализации, какой вариант использовать. Обязательные зависимости выбранных модулей добавляются автоматически. Неизвестный модуль, отсутствующая реализация, цикл зависимостей или зависимость от другой стороны приводят к ошибке сборки.

### Что попадает в опубликованную игру

Установленный SDK движка содержит каталог всех доступных производственных модулей. Это каталог для выбора, а не готовая поставка целиком.

При сборке каждой стороны SDK разрешает её профиль и использует только выбранные модули с их обязательными зависимостями. Варианты реализации, которые не были выбраны, и несвязанные модули в игровой пакет не попадают. Общие библиотеки, необходимые выбранным модулям, включаются как их зависимости.

Профиль задаётся элементами `KarpikModuleSelection` в настройках сборки игры. Например, можно включить общие игровые системы и логирование для всех сторон, а клиентскую графику указать только в профиле клиента. Для модулей с вариантами реализации в профиле указывается ровно один выбранный вариант.

По умолчанию используется статическая композиция: SDK формирует состав модулей и сервисов при сборке исполняемого файла. В этом режиме отдельные файлы модулей и их манифест для запуска не нужны. Поддерживается и динамический режим: выбранные модули включаются в runtime-пакет и загружаются при запуске. Динамический режим также использует профиль сборки и не загружает весь каталог SDK.

Таким образом, ответ на вопрос о публикации: **неиспользуемые модули не включаются в игровую поставку**. Исключение — модуль, который не выбран явно, но нужен как обязательная зависимость другого выбранного модуля.

## SDK игровых проектов

Игровой проект может находиться отдельно от репозитория движка и использовать установленную версию KarpikEngine. Версия SDK указывается в конфигурации решения, поэтому сборка использует совместимый набор инструментов и модулей.

Каждый проект решения помечается своим назначением и стороной: например, игровой runtime клиента, сервера, общий код, тесты или инструменты. SDK проверяет граф всего решения до компиляции:

- все проекты соблюдают правила SDK;
- ссылки между проектами объявлены явно и образуют допустимый граф;
- в графе нет циклов и запрещённых переходов между клиентом, сервером и общим кодом;
- профиль модулей соответствует доступным модулям и их обязательным зависимостям.

Это позволяет находить ошибки структуры проекта во время сборки, а не после запуска игры. SDK также связывает сборку с подготовкой ресурсов, разрешением модулей и созданием отдельных runtime-пакетов клиента и сервера. Сборка из редактора и обычная командная сборка используют одну и ту же модель проекта.

Тип проекта и его сторона задаются в самом проекте:

```xml
<Project Sdk="Karpik.Engine.Sdk">
  <PropertyGroup>
    <KarpikProjectKind>Runtime</KarpikProjectKind>
    <KarpikSide>Client</KarpikSide>
  </PropertyGroup>
</Project>
```

## Content Pipeline

Content Pipeline превращает исходные игровые ресурсы в проверенный набор данных, который включается в сборку игры. Он отделяет рабочие исходники от файлов, используемых runtime.

### Описание ресурсов

Рядом с исходником хранится файл метаданных. В нём указываются:

- неизменяемый идентификатор ресурса;
- логическое имя, по которому ресурс удобно находить в игре;
- тип исходных данных и настройки обработки;
- зависимости от других ресурсов;
- целевая сторона: клиент, сервер или обе стороны.

Идентификатор не меняется при перемещении или переименовании файла. Логическое имя можно менять отдельно. Pipeline проверяет корректность метаданных, уникальность идентификаторов и имён, зависимости и соответствие ресурсов выбранной стороне сборки.

### Подготовка и включение в игру

При сборке Pipeline проверяет исходники, обрабатывает выбранные ресурсы, формирует манифест и готовые артефакты. Результат детерминирован: одинаковые входные данные дают одинаковую сборку. Публикация результата атомарна — если обработка завершается ошибкой, предыдущая успешная версия остаётся доступной.

Для клиентской и серверной частей формируются собственные наборы ресурсов с учётом их целевой стороны. SDK автоматически помещает манифест и артефакты в соответствующие runtime-пакеты.

### Поддерживаемые данные и текущие границы

Сейчас поддержаны игровые данные в формате JSON, изображения, описания шрифтов и исходные файлы графических эффектов. Для JSON по метаданным генерируются типизированные ссылки, которые можно использовать из кода игры.

Подготовка изображения пока проверяет и упаковывает исходные данные, но не создаёт готовый графический объект. Описания шрифтов и графические исходники также проверяются и включаются в поставку как данные; создание runtime-шрифта и компиляция графических эффектов пока не входят в Pipeline.

### Загрузка в runtime

При запуске реестр ресурсов читает манифест и получает сведения обо всех доступных ресурсах, не загружая сразу содержимое каждого файла. Игровой код запрашивает нужный ресурс через типизированную ссылку. Чтение файла и преобразование данных выполняются явно, до использования ресурса в игровом цикле.

### Работа с ресурсами в редакторе

При открытии проекта редактор может создать отсутствующие метаданные для поддерживаемых типов файлов. Для выбранного ресурса можно менять тип, логическое имя, сторону использования, настройки обработки и зависимости. Идентификатор показывается только для чтения. Перед сохранением редактор проверяет метаданные и не заменяет файл невалидными данными.

## Сервисы: регистрация и использование

Сервис регистрируется под контрактом — обычно это интерфейс, который используют игровые системы и другие сервисы. Для обычной регистрации тип помечается двумя атрибутами:

```csharp
using System.Composition;
using Karpik.Engine.Core;

public interface IInventoryService
{
    void UpdateInventory();
}

[Export(typeof(IInventoryService))]
[ServiceRegistration(ModuleScope.Simulation, ServiceLifetime.Singleton)]
public sealed class InventoryService : IInventoryService
{
    public void UpdateInventory() { }
}

public sealed class InventorySystem(IInventoryService inventory) : ISystemUpdate
{
    public void Update()
    {
        inventory.UpdateInventory();
    }
}
```

`Export` задаёт контракт, доступный другим частям игры. `ServiceRegistration` задаёт область жизни сервиса и срок его существования. Зависимости передаются через конструктор; зарегистрированные сервисы и игровые системы создаются движком.

Области образуют иерархию:

- `Engine` — инфраструктура одного работающего процесса;
- `ModSet` — сервисы, общие для симуляций с одним набором модов;
- `Simulation` — сервисы и состояние одной игровой симуляции.

Дочерняя область видит сервисы родительских областей, но соседние симуляции изолированы. `Singleton` означает один экземпляр на область-владельца, а не один экземпляр на весь процесс. `Transient` создаёт новый экземпляр при каждом разрешении.

Если нужны готовый экземпляр, фабрика, условная регистрация или регистрация типа, который нельзя пометить атрибутами, модуль регистрирует сервисы через `IModuleInstaller.OnRegisterServices`. Такие явные регистрации выполняются после атрибутных и могут намеренно их переопределить.

## Настройка журналирования игрой

Движок передаёт сервисам типизированный журнал через конструктор. По умолчанию сообщения выводятся в консоль; при работе с редактором доступен сбор сообщений в его панели.

Игра может изменить конфигурацию журналирования, добавив сервис `ILoggerFactoryModifier`. Движок вызывает его один раз при создании фабрики журналирования, до запуска игровой симуляции. Через переданный ему `ILoggingBuilder` можно:

- добавить собственный приёмник сообщений, например для записи в файл или передачи в свою систему;
- настроить фильтры и минимальный уровень сообщений;
- очистить стандартные приёмники и заменить их собственными.

```csharp
using System.Composition;
using Karpik.Engine.Core;
using Karpik.Engine.Shared.Log;
using Microsoft.Extensions.Logging;

[Export(typeof(ILoggerFactoryModifier))]
[ServiceRegistration(ModuleScope.Engine, ServiceLifetime.Singleton)]
public sealed class GameLoggingModifier : ILoggerFactoryModifier
{
    public void Modify(ILoggingBuilder builder)
    {
        builder.ClearProviders();
        // GameLogProvider — собственный приёмник сообщений игры.
        builder.AddProvider(new GameLogProvider());
    }
}
```

Приёмники, подключённые через фабрику, освобождаются вместе с ней. Настройка выполняется при запуске и не добавляет работы в игровой цикл.

## Перезапуск с сохранением состояния

Во время разработки клиент или сервер можно перезапустить отдельно. Игровые миры сериализуются и восстанавливаются в новом процессе; временные ресурсы, соединения и процессные дескрипторы создаются заново. Это позволяет обновлять код, не теряя переносимое игровое состояние.
