# Требования к скриптовым модам

> Уточнения от 2026-10-06: [актуальная спецификация](script-modding-design.md).
> При расхождении решений приоритет имеет этот новый документ. Ниже сохранена
> предыдущая редакция требований; она не подтверждает текущую реализацию.

Дата: 2026-10-03.
Статус: согласованные требования первой версии; технический дизайн ещё не утверждён.

Этот документ сохраняет решения из обсуждения поддержки модов. Он служит
исходными требованиями для будущего ExecPlan по `plans/PLANS.md`, а не планом
реализации. Неописанные возможности не считаются автоматически включёнными
в первую версию.

## Цель

Мод должен уметь создавать новые игровые механики и изменять существующие через
публичные точки расширения движка. Для этого модам нужны сервисы движка,
собственные компоненты и системы, доступ к штатным компонентам и свой контент.

## Бэкенды исполнения

- Lua — первый поддерживаемый скриптовый бэкенд.
- Архитектура должна допускать другие подготовленные бэкенды. Подготовленный
  бэкенд реализует общий контракт доступа к возможностям движка.
- Общие данные компонентов и события не должны зависеть от конкретного языка.
  Моды разных бэкендов должны иметь возможность работать с данными друг друга.
- Это не означает, что один исходный скрипт обязан исполняться на любом бэкенде.
- Межмодовые вызовы экспортированных функций, включая вызовы между бэкендами,
  в первую версию не входят.
- Каждый мод получает отдельное скриптовое окружение в каждой симуляции.
  Локальные переменные и функции одного мода не становятся общим окружением
  остальных модов.

Выбор конкретного интерпретатора Lua и устройство его интеграции пока открыты.
Отдельное окружение не означает уже принятое решение об отдельной VM или процессе.

## Shared, Server и Client

Мод может объявлять общую, серверную и клиентскую части.

- Shared содержит общие определения и логику, доступную для вызова как с Client,
  так и с Server.
- Server содержит серверную часть мода и использует доступные ей возможности.
- Client содержит клиентскую часть мода и использует доступные ей возможности.
- Размещение кода в Shared само по себе не задаёт, кто его вызывает, где
  выполняется система и как синхронизируются результаты.
- Состояние и выполнение на Client и Server раздельны. Общий код не означает
  общую память между сторонами.
- Ограничения Client / Server / Shared и правила авторитетности существующего
  движка сохраняются.

## Скоупы и жизненный цикл

Используется существующая цепочка `Engine -> ModSet -> Simulation`.

- ModSet фиксирует набор модов, их схемы компонентов, контент и регистрации
  систем. Набор модов не меняется во время жизни этого скоупа.
- Simulation владеет ECS мирами, изменяемым игровым состоянием, скриптовыми
  окружениями и экземплярами скриптовых систем конкретной симуляции.
- Client и Server создают свои экземпляры скоупов для соответствующих частей
  модов вместе с Shared.
- Изменение набора модов требует создания нового ModSet и пересоздания
  зависимых симуляций.
- Загрузка симуляции начинается только после успешной проверки набора модов.

Перезагрузка кода внутри неизменного набора модов — отдельный вопрос hot reload.
Она не считается согласованной возможностью первой версии только из-за наличия
ModSet.

## Сервисы и доступ к платформе

- Моды используют сервисы через явно предоставленный API движка.
- Доступные операции зависят от стороны выполнения.
- Файлы, сеть и ОС доступны только через API движка.
- Прямые возможности скриптового runtime для обхода этого API не предоставляются.
  Правило распространяется и на будущие бэкенды.

Перечень опубликованных сервисов и операций ещё предстоит определить.

## Компоненты и данные

- Мод может объявлять собственные компоненты по схемам данных.
- Схемы фиксируются в ModSet и не меняются во время его жизни.
- Добавлять поля в компонент движка или другого мода нельзя. Дополнительные
  данные оформляются собственным компонентом на той же сущности.
- Любой зарегистрированный компонент доступен другим модам для чтения и
  изменения через ECS API. Отдельное разрешение автора мода на доступ к его
  компоненту не требуется.
- Скриптовые системы могут читать и изменять опубликованные штатные компоненты
  движка, а также компоненты модов.
- Запросы должны позволять совместно использовать штатные и модовые компоненты.
- Доступ штатных C# систем к модовым компонентам через этот API не требуется.
  Общий API предназначен для скриптовых бэкендов; внутренний C# код реализации
  хранилища и мостов этим ограничением не исключается.
- Доступ учитывает ограничения стороны и инварианты штатных компонентов.
- Мод не получает долгоживущие ссылки или указатели на память ECS пулов.

Строки и типизированные коллекции входят в требования к данным компонентов.
Несколько компонентов могут ссылаться на одну общую коллекцию. Она является
отдельным ресурсом хранилища Simulation, а компоненты содержат проверяемые
дескрипторы, не прямые указатели. Изменения общей коллекции видны через все
ссылки на неё. Удаление одного компонента не уничтожает коллекцию, используемую
другими компонентами. Выбран счётчик ссылок с явным API: специальный метод
получения доступа увеличивает счётчик, функция освобождения уменьшает его.
При нулевом счётчике хранилище освобождает коллекцию. Полученную владеющую ссылку
нужно освобождать; простое копирование дескриптора не заменяет операцию получения
такой ссылки. Циклы владеющих ссылок допускаются, но мододел обязан явно
разрывать их перед освобождением ресурсов. Автоматический сборщик циклов
не требуется.
Запись ссылки в поле компонента через API автоматически удерживает коллекцию.
Замена ссылки или удаление компонента освобождают прежнее владение поля.
Ссылка самого скрипта учитывается отдельно и освобождается явно.
Скрипт может хранить такую владеющую ссылку между вызовами системы и между
тиками; возврат из вызова сам по себе не освобождает её.
Перемещение записи внутри sparse set переносит владение без изменения счётчика.
Для ссылочных элементов коллекций действует тот же автоматический учёт:
добавление удерживает вложенную коллекцию, удаление или замена освобождают
прежнюю ссылку элемента. При освобождении самой коллекции освобождаются
владеющие ссылки её элементов. Циклы по-прежнему разрывает мододел вручную.
Ошибка и отключение одной системы не освобождают её скриптовые ссылки:
окружение мода остаётся активным, и ссылки могут использовать другие системы.
При уничтожении окружения движок освобождает все оставшиеся владения этого
окружения. Владения полей компонентов, элементов коллекций и других окружений
учитываются отдельно; удерживаемый ими ресурс сохраняется. Циклы владения
по-прежнему требуют ручного разрывания; при завершении всей Simulation её
хранилища уничтожаются целиком.

Нужен отдельный диагностический метод для обнаружения циклов владения.
Предусматривается возможность визуализации ресурсов хранилища и связей между
ними: коллекции, владельцы ссылок, счётчики и объёмы занятой/зарезервированной
памяти. Конкретное представление, место в инструментах и режим сбора сведений
ещё не определены. Диагностика не должна автоматически освобождать ресурсы
и не должна добавлять обход графа или построение визуализации в обычный тик.
Охват аллокаций самих скриптовых runtime требует отдельного решения.
Их хранением и жизненным циклом управляет движок; они доступны через общий API,
а не через таблицы конкретного скриптового языка. Точный набор типов полей,
представление строк, коллекций и вложенных данных ещё не определены.

Данные должны быть пригодны для плотного хранения и пакетной обработки.
Для динамических компонентов выбрано собственное хранилище в движке,
привязанное к сущностям Dragon. Общий API объединяет доступ к штатным и модовым
данным. Для каждой схемы выбрана структура sparse set: плотные записи сущностей
и данных с индексом наличия по слоту сущности. Это не архетипное хранилище.
Исходная раскладка полей — AoS: поля одной записи компонента находятся рядом,
записи расположены плотно. Переход на SoA рассматривается по результатам измерений.
Ёмкости и устройство смешанных запросов ещё не утверждены;
модовые схемы не становятся штатными CLR типами Dragon автоматически.

Пока у сущности есть модовые компоненты, движок удерживает на ней внутренний
компонент Dragon `ModDataAnchor`. После удаления последнего модового компонента
якорь снимается; оставшиеся штатные компоненты продолжают удерживать сущность.
Явное удаление сущности очищает её модовые данные и принадлежащие им ресурсы.

Добавление и удаление компонентов применяются немедленно, включая изменения
во время работы системы. Буферизация до конца системы не выбрана.
Перед обходом кандидаты запроса записываются в заранее зарезервированный
переиспользуемый массив идентификаторов сущностей с учётом их поколений.
Обход идёт по этому массиву, без копирования значений компонентов. Перед выдачей
сущности проверяются её жизнь и текущее соответствие запросу; данные читаются
актуальные. Новые кандидаты, появившиеся после формирования массива, видны
следующему запросу. Переносы записей sparse set не меняют массив активного обхода.
Активные вложенные обходы не должны перезаписывать буферы друг друга.
Ёмкости буферов и поведение при их исчерпании ещё предстоит определить.
Этот документ не утверждает, что скриптовая схема уже может стать новым
`struct : IEcsComponent` или новым `EcsPool<T>` в собранном NativeAOT приложении.

## Системы и события

- Мод может регистрировать собственные скриптовые системы.
- Системы подключаются к жизненному циклу и планированию систем движка.
- Порядок выполнения систем задаётся отдельно от порядка загрузки модов.
- Должна поддерживаться настройка порядка относительно других систем через
  общий механизм планирования движка.
- Игровая логика использует фиксированный шаг времени по правилам движка.
- События представлены сущностями с компонентами, как в самом движке.
- Системы обрабатывают события обычными ECS запросами; отдельная межмодовая
  шина событий не требуется.
- Жизненный цикл событий следует существующим правилам движка.

## Ошибки исполнения и длительные вычисления

- Ошибка исполнения отключает сбойную скриптовую систему; остальные системы
  продолжают работу.
- Диагностика должна идентифицировать мод, систему и причину ошибки.
- Автоматический откат уже внесённых системой изменений не предусмотрен.
- Автоматического бюджета инструкций или времени исполнения нет.
- Автоматическая приостановка или отключение системы из-за длительности
  вычисления не предусмотрены.
- Мододел при необходимости самостоятельно распределяет вычисление по тикам.

Принятое следствие: длительный вызов задерживает симуляцию, а бесконечный цикл
может заблокировать её поток. Отключение системы при ошибке этого не предотвращает.
Отсутствие бюджета скрипта не отменяет требований к производительности API движка.

## Контент и изменение механик

- Мод может добавлять собственный контент через pipeline движка.
- Существующие механики изменяются через публичные точки расширения:
  предусмотренные правила, операции и переопределения.
- Если несколько модов изменяют общий контент, изменения применяются
  последовательно в фиксированном порядке.
- Отдельные указания «загрузиться до/после другого мода» без зависимости
  не поддерживаются.

Точный алгоритм порядка для независимых модов не утверждён. Сортировка по
стабильному ID была предложена, но пока не является согласованным решением.

## Зависимости и проверка ModSet

- Manifest поддерживает обязательные и опциональные зависимости с требованиями
  к совместимости версий.
- Зависимости могут объявляться отдельно для Shared, Server и Client.
- Зависимости Shared проверяются на обеих сторонах, остальные — на своей стороне.
- Отсутствующая обязательная зависимость — ошибка загрузки.
- Отсутствующая опциональная зависимость допустима: мод работает без интеграции
  с отсутствующим модом.
- Установленная зависимость с несовместимой версией — ошибка загрузки, даже
  если зависимость опциональная.
- Циклические зависимости — ошибка загрузки, включая циклы с присутствующими
  опциональными зависимостями.
- Ошибка проверки отменяет загрузку всего ModSet. Проблемные моды не исключаются
  автоматически ради запуска оставшейся части набора.

При присутствующей совместимой опциональной зависимости мод может дополнять
данные или поведение другого мода через общие контракты. Точная схема manifest,
синтаксис диапазонов версий и способ объявления условной интеграции пока открыты.

## Сохранение состояния

- Данные компонентов модов сохраняются и восстанавливаются вместе со штатным
  состоянием симуляции уже в первой версии.
- Формат данных компонентов не зависит от скриптового бэкенда.
- Для загрузки сохранения требуется тот же набор модов и те же версии,
  с которыми оно было создано.
- При несовпадении загрузка отменяется.
- Миграции сохранений между версиями модов не входят в первую версию.

Автоматическое сохранение произвольных локальных переменных, замыканий,
корутин и прочего внутреннего состояния интерпретатора не согласовано.

## Сетевая синхронизация

- Мод явно объявляет синхронизируемые компоненты и поля в их схемах.
- Неотмеченные данные остаются локальными для соответствующей стороны.
- Используется общий механизм синхронизации движка, а не отдельная сетевая
  модель для модов. Правила авторитетности и доставки следуют контрактам движка.
- Схемы синхронизируемых данных модов учитываются при проверке сетевой
  совместимости.

Текущие C# контракты находятся в
`Modules/Shared/Network.Shared/Network.Shared.Core/ComponentAttribute.cs`
(`NetworkedComponent`, `NetworkedField`). Генератор
`Network.Codegen/Network.Codegen/NetworkGenerator.cs` создаёт snapshot код
для известных при сборке C# компонентов. Динамические схемы ModSet потребуется
подключить к общему snapshot pipeline; существование готового адаптера этим
документом не утверждается.

## Отложенная цель

Отключение и полная замена произвольных штатных систем модом остаётся желаемым
идеалом за пределами текущей версии. Достижимость этой цели пока не подтверждена.
Она не должна определять обязательный объём первой реализации.

## Ограничения и открытые технические решения

Статическая композиция и NativeAOT остаются исходными ограничениями проекта;
см. `docs/02_ADR/static-runtime-composition.md`. Lua — выбор языка первой версии,
но не уже утверждённая библиотека или способ загрузки runtime.

Перед планированием реализации необходимо определить:

- общий контракт бэкендов и выбор Lua runtime;
- представление и регистрацию динамических компонентов в Dragon ECS;
- типы полей, хранение строк и коллекций и допустимые операции с ними;
- мост к штатным компонентам и сервисам с сохранением их инвариантов;
- формат manifest, идентификаторы и порядок независимых модов;
- подключение модового контента к существующему pipeline;
- сериализацию динамических схем для сохранений и сетевых snapshots;
- безопасную границу отключения системы после частично выполненного вызова.

Это вопросы дизайна, а не разрешение реализовать произвольный вариант.
Следующий этап — исследование существующих механизмов и подготовка дизайна,
затем ExecPlan. Код реализации этим документом не добавляется.
