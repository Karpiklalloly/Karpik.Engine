# Подключение скриптовых модов к существующему runtime

Дата: 2026-10-03.
Проверенный commit: `59a718b585b82f7538bd7eb9dfc61a3cada87262`.
Статус: исследование исходников; выбран вариант собственного хранилища в движке,
детали интеграции ещё требуют согласования.
Требования: [script-modding-requirements.md](script-modding-requirements.md).

## Основной вывод

Требования можно проектировать поверх существующего движка, но готового пути
регистрации произвольной скриптовой схемы как обычного Dragon компонента нет.
Существующие компоненты, системы, сохранение и сетевые snapshots в ключевых
местах опираются на CLR типы, известные при сборке.

Выбранный разработчиком путь: движок хранит динамические данные
в отдельных плотных хранилищах, привязанных к сущностям Dragon, а общий API
объединяет доступ к штатным и модовым компонентам. Сохранение, сеть и планировщик
потребуют явных точек подключения этих хранилищ и скриптовых систем.

Направление согласовано 2026-10-03: добавить собственное хранилище модовых
компонентов в движке. Конкретное устройство ещё не утверждено и не проверено
прототипом. Модовые схемы не становятся отдельными `EcsPool<T>` и штатными
`EcsAspect` автоматически; общий API и смешанные запросы нужно спроектировать.

Также согласовано: штатным C# системам не нужен доступ к модовым компонентам
через общий API. Этот API предназначен для скриптовых бэкендов; адаптеры к
штатным C# компонентам обслуживают вызовы скриптов. Внутренний код реализации
хранилища по-прежнему может быть C#.

## Что проверено

Исследованы исходники Dragon ECS, ECS state provider, converter и snapshot
генератор, схема handshake, реестр систем и построитель графа исполнения.
Сопоставлены действующие исходники с архитектурными документами:

- `docs/02_ADR/static-runtime-composition.md`;
- `plans/ecs-state-serialization-execplan.md`;
- `docs/02_ADR/scheduler-jobs-runtime.md`;
- `third-parties/DragonECS/AGENTS.md`.

Его кандидаты использованы только для навигации; выводы проверены по исходникам.

## 1. Компоненты Dragon ECS

Для собственного хранилища разработчик выбрал sparse set: отдельный набор
для каждой схемы с плотными сущностями/данными и sparse индексом по слоту
сущности. Архетипная группировка по полному набору компонентов не используется.
При удалении записи переносится последняя плотная запись и обновляется её
sparse индекс. Доступ должен учитывать поколение сущности и её мир.
Исходной раскладкой выбрана AoS: поля одной записи компонента находятся рядом,
записи расположены плотно. Размер записи, смещения и выравнивание полей
определяются по схеме при подготовке хранилища. Это не требует генерации CLR
типов. Возможный переход на SoA оценивается по результатам измерений.

### Наблюдения

- `third-parties/DragonECS/src/Pools/EcsPoolBase.cs:16` предоставляет публичный
  контракт пользовательских пулов `IEcsPoolImplementation`; на строке 51 есть
  типизированный маркер `IEcsPoolImplementation<T>`.
- `third-parties/DragonECS/src/EcsWorld.pools.cs:275` инициализирует пользовательский
  пул. На строках 282–319 идентичность связана с CLR типом пула и компонента;
  повторное использование занятых идентификаторов отвергается.
- `third-parties/DragonECS/src/EcsMask.cs:466` и далее принимает `Type` и
  `EcsTypeCode`. Это динамическое построение маски существующих типов, а не
  регистрация новой схемы по строковому имени или описанию полей.

Следствие: один класс пользовательского пула с разным значением `SchemaId`
не создаёт неограниченное число независимых компонентов Dragon. Генерация
новых CLR типов при загрузке не подходит принятой статической/NativeAOT модели.
Наличие пользовательских пулов само по себе проблему не решает.

### Варианты

| Вариант | Возможности и цена |
| --- | --- |
| Отдельные динамические хранилища в движке | Совместимы с фиксированным исполняемым кодом; нужны объединённые запросы и явная интеграция жизненного цикла. Штатный `world.Where` не различает модовые схемы автоматически. |
| Расширение Dragon для схем без CLR типов | Потенциально даёт более прямую интеграцию масок и пулов, но затрагивает идентичность типов, хранение, запросы и инструменты. Требует отдельного решения и разрешения менять Dragon. |
| Генерация C# компонентов до сборки хоста | Сохраняет штатные пулы, но требует пересборки под набор модов и не удовлетворяет самостоятельной загрузке новых скриптовых схем в готовый runtime. |

Для первого дизайна выбран вариант отдельных хранилищ в движке. Сущности
остаются сущностями Dragon, а общая семантика компонентов предоставляется
API движка. Остальные варианты оставлены как рассмотренные альтернативы.

### Условия корректности рекомендуемого варианта

- ModSet содержит неизменные схемы и разрешённые операции; Simulation содержит
  значения, индексы, строки, коллекции и связанные ресурсы.
- Для каждой схемы нужны плотные данные и индекс наличия по сущности.
  Поиск схем и полей выполняется при регистрации/подготовке вызова; горячие
  операции используют проверенные идентификаторы и индексы.
- Смешанный запрос пересекает штатную выборку Dragon с индексами модовых
  компонентов. Не следует делать полный обход всех сущностей на каждый запрос.
- Для удержания сущности с модовыми данными выбран внутренний заранее известный
  компонент Dragon `ModDataAnchor`. Он присутствует, пока есть хотя бы один
  модовый компонент. При удалении последнего модового компонента якорь снимается;
  оставшиеся штатные компоненты продолжают удерживать сущность. Явное удаление
  сущности очищает модовые данные и принадлежащие им ресурсы.
- Нельзя считать сырой `int` постоянным идентификатором: нужно учитывать мир,
  поколение сущности, повторное использование слота и миграцию между мирами.
- `third-parties/DragonECS/src/EcsWorld.cs:734` уведомляет об удалении через
  `IEcsEntityEventListener`; cleanup пулов отложен. На строках 2026–2036
  объявлены публичные listener контракты мира и сущностей. Их порядок следует
  проверить прототипом, включая явное удаление структурного компонента.
- `Modules/Shared/ECS/ECS.Core/WorldEventListener.cs:13` уже использует публичные
  listeners. Их нужно привязывать к Simulation и отписывать при disposal.

Выбраны AoS раскладка и удерживающий компонент `ModDataAnchor`. Пока не утверждены
его конкретные поля, смещения и выравнивание полей модовых записей, алгоритм
построения запросов и политика ёмкости хранилищ и буферов.

Структурные изменения выбраны немедленными: добавления и удаления не ждут
завершения системы. Для активного обхода выбран заранее зарезервированный
переиспользуемый массив идентификаторов кандидатов с учётом поколений сущностей.
Перед выдачей каждой сущности проверяются её жизнь и текущее соответствие запросу.
Массив фиксирует состав кандидатов, но не копирует значения компонентов;
данные читаются актуальные. Появившиеся после формирования массива кандидаты
видны следующему запросу. Вложенные активные обходы должны иметь независимые
участки памяти, чтобы не перезаписывать списки друг друга. Ёмкости и поведение
при исчерпании подготовленной памяти остаются открытыми решениями.

## 2. Штатные компоненты и API бэкендов

Для C# компонентов предлагаются адаптеры, подготовленные при сборке хоста:
они выполняют типизированный доступ к `EcsPool<T>` и предоставляют бэкендам
проверенные операции чтения/записи. Для динамических компонентов те же операции
работают с хранилищами схем.

Строки и коллекции остаются данными движка.
Общие коллекции между несколькими компонентами согласованы: коллекция является
отдельным ресурсом Simulation, компоненты хранят проверяемые дескрипторы.
Изменения через любой дескриптор видны остальным пользователям коллекции.
Удаление одного компонента не должно уничтожать ещё используемую коллекцию.
Выбран явный API получения/освобождения со счётчиком ссылок: получение доступа
увеличивает счётчик, освобождение уменьшает, ноль освобождает ресурс.
Для полей компонентов согласован автоматический подсчёт владельцев:
запись через API удерживает новую коллекцию, замена или удаление компонента
освобождают прежнюю ссылку поля. Ссылки скрипта учитываются отдельно и
освобождаются явно. Скриптовые владеющие ссылки могут сохраняться между
вызовами системы и тиками; возврат из вызова не означает освобождение ссылки.
Перенос записи sparse set не создаёт нового владельца.
Тот же автоматический учёт согласован для ссылочных элементов коллекций:
добавление удерживает вложенный ресурс, удаление или замена освобождают прежнюю
ссылку; уничтожение коллекции освобождает её исходящие владеющие ссылки.
Обработка глубокой цепочки освобождений должна избегать неограниченной рекурсии;
детали реализации ещё не выбраны. Циклы требуют ручного разрывания.
Согласовано: ошибка и отключение одной системы не освобождают скриптовые ссылки,
так как они могут использоваться другими системами живого окружения мода.
При уничтожении окружения движок освобождает все его оставшиеся владения.
Владения компонентов, коллекций и других окружений учитываются отдельно.
Отслеживание этих владений и конкретный порядок disposal ещё требуют дизайна;
циклы не становятся автоматически собираемыми от освобождения внешних ссылок.
Цикл владеющих ссылок остаётся отдельной проблемой:
освобождение внешних ссылок не обнуляет счётчики взаимно удерживающих коллекций.
Для циклического владения согласовано ручное разрывание циклов мододелом;
автоматический сборщик циклов не требуется. Нужен отдельный диагностический
метод обнаружения циклов и возможность визуализации памяти хранилища и связей
владения. Одного счётчика для графа недостаточно: диагностике нужны сведения
об источниках владеющих ссылок. Способ их получения, включая ссылки из скрипта,
ещё не выбран. Невладеющие связи не должны учитываться как удерживающие ресурс.
Поиск циклов и построение визуализации выполняются отдельно от обычного тика;
согласованный снимок данных и расходы инструментирования требуют дизайна.
Диагностика ничего автоматически не освобождает. Профилирование внутренних
аллокаций интерпретатора не считается уже выбранным механизмом этой диагностики.

Скрипт получает доступ к значениям,
но не владеет указателями или долгоживущими `ref` на пулы. Структурная запись,
перераспределение буфера и уничтожение сущности должны инвалидировать связанные
представления по определённому контракту.

Не следует публиковать всякое поле штатного компонента простым setter: некоторые
изменения требуют операции сервиса, например согласования с физикой. Список
таких операций и генерация адаптеров требуют отдельного дизайна.

## 3. Сохранение и восстановление

### Что существует сейчас

- `Modules/Shared/ECS/ECS.Core/EcsRestartWorkerStateProvider.cs:29` сохраняет
  три мира: default, event и meta. Внешний envelope использует source-generated
  System.Text.Json, внутренние snapshots остаются JSON строками.
- `Modules/Shared/ECS/ECS.Core/EcsWorldExtensions.cs:18` перечисляет компоненты
  Dragon через `GetComponentsFor` и сериализует `EntitySnapshot` с
  `TypeNameHandling.Objects`.
- `Modules/Shared/ECS/ECS.Core/AssetManagement/Converters/ComponentArrayConverter.cs:31`
  восстанавливает компоненты через `$type`, binder и `ToObject(Type, serializer)`.
- `Modules/Shared/ECS/ECS.Core/EcsWorldExtensions.cs:59` материализует компоненты перед удалением прежних
  сущностей, затем создаёт сущности с сохранёнными числовыми IDs и применяет
  templates. Это предварительная проверка, а не доказательство полной
  транзакционности всей операции restore.
- `plans/ecs-state-serialization-execplan.md` описывает будущий бинарный registry,
  но его implementation milestones не завершены. Его нельзя считать готовым API.

Отдельное динамическое хранилище не попадает в текущий JSON snapshot автоматически.
Исследован restart-state путь; полноценная система игровых save-файлов этим
исследованием не подтверждена.

### Предлагаемое подключение

Расширить общий state envelope секцией ModSet manifest и schema hash, значений
модовых компонентов и принадлежащих им строк/коллекций. Проверять версии,
схемы и корректность payload до разрушения текущего состояния.

Нужно явно восстановить соответствие сущностей и их поколений, затем ссылки
между сущностями. Локальные handle строк, буферов и объектов runtime не являются
форматом сохранения; сохраняются значения или устойчивые идентификаторы.

Использовать контракт `IRestartWorkerStateProvider` как одну из точек интеграции,
но не сериализовать два вида хранения независимо без общего порядка и проверки
совместимости. Переход штатных компонентов на бинарные codecs — существующая
отдельная задача; не нужно молча включать полную её реализацию в поддержку модов.

## 4. Сетевая синхронизация

### Что существует сейчас

- `Network.Codegen/Network.Codegen/NetworkGenerator.cs:65` обнаруживает C#
  компоненты в сборке и references; диагностикой требует unmanaged struct,
  реализующий `IEcsComponent`.
- На строке 194 находится конечный перечень поддержанных codecs: числа,
  bool, Color и несколько векторных типов. Строки и переменные коллекции
  текущий генератор этим перечнем не поддерживает.
- На строках 234–256 генерируется доступ к конкретному `EcsPool<T>`.
- `WriteSnapshot` на строке 290 и `ApplySnapshot` на строке 307 задают
  текущий формат записи/применения. Это не уже существующий registry
  пользовательских runtime serializers.
- `ApplySnapshot` создаёт отображение NetworkId в локальную сущность.
  Нельзя передавать локальный `entlong` как универсальную сетевую ссылку.
- `Modules/Shared/Network.Shared/Network.Shared.Core/NetworkSchemaHandshake.cs:10`
  передаёт schema hash и отвергает несовпадение.

### Предлагаемое подключение

Расширить существующий snapshot pipeline точкой записи и чтения модовых данных,
используя тот же transport, идентичность сетевых сущностей и правила движка.
Штатные C# codecs остаются сгенерированными; модовые codecs подготавливаются
по зафиксированным схемам до запуска симуляции.

Подготовленный codec здесь означает проверенный план операций над известными
типами полей, а не runtime генерацию CLR кода.

В общий handshake включить совместимый wire schema модов. Локальные Client-only
и Server-only поля не должны случайно делать эту схему различной на сторонах.
Точный контракт согласования manifest и частей модов ещё требуется определить.

Для строк/коллекций нужны явные длины, проверка payload и политика памяти.
Это формат данных и защита корректности, а не отвергнутый пользователем бюджет
времени/инструкций. Дескрипторы локальных буферов не отправляются как их содержимое.

Ссылки на сущности требуют ремаппинга через NetworkId, включая ссылки на сущности,
которые ещё не созданы при чтении текущей записи. Удаления должны очищать оба
вида хранения. Коллизии идентификаторов схем проверяются до начала обмена.

## 5. Регистрация и порядок скриптовых систем

Обнаружен дополнительный блокер, влияющий на согласованные требования:

- `Karpik.Engine.Core/Services/ISystemRegistry.cs:5` регистрирует систему по `T`.
- `Karpik.Engine.Core.Runner/SystemRegistry.cs:10` использует `HashSet<Type>`;
  на строке 36 отвергает повторную регистрацию одного типа.
- `Karpik.Engine.Core/Scheduling/EcsUpdateGraphBuilder.cs:18` и 30 использует
  Type как ключ descriptors и зарегистрированных систем; дубликаты отвергаются.

Регистрация каждого Lua обработчика как одного и того же `ScriptSystemAdapter`
через обычный `Add<T>` не решает задачу. Один общий runner, выполняющий все
скрипты подряд, тоже недостаточен: он не обеспечивает независимое расположение
скриптовых систем между штатными системами.

Предлагается расширить engine-level идентичность узла исполнения: штатные узлы
сохраняют привязку к Type, скриптовые получают стабильный ключ мода/системы.
Декларации доступа учитывают штатные и модовые компоненты, а порядок собирается
до запуска Simulation. Конкретная форма расширения требует отдельного дизайна.
В первой реализации нельзя автоматически запускать Lua системы параллельно
без доказательства безопасности окружений, структурных операций и доступа к данным.

## Реальное время и память

Отсутствие бюджета выполнения скрипта — принятое требование. Оно не делает
вызов интерпретатора или рост коллекции операцией с предсказуемой задержкой.
GC Lua и длительность пользовательского кода остаются отдельными расходами.

В мосте движка следует исключить reflection, boxing, LINQ, выделение wrappers
на сущность и поиск имён в горячих циклах. Схемы, планы codecs и запросов
подготавливаются заранее; массовые операции предлагаются пакетно.

Строковые изменения и рост переменных коллекций требуют согласованной политики
ёмкости. Пока не доказано, что все такие операции обеспечат отсутствие выделений.
Нельзя обещать 0 B и предсказуемую задержку без измерений и определения поведения
при исчерпании подготовленной памяти. Это не основание убирать согласованную
поддержку строк и коллекций или вводить отвергнутый бюджет скриптов.

## Следующие проверки до реализации

После выбора варианта хранения подготовить ExecPlan по `plans/PLANS.md`.
В него включить небольшой проверочный прототип и следующие наблюдаемые сценарии:

1. Две динамические схемы, штатный компонент и смешанный запрос без генерации
   CLR типов. Сущность только с модовыми данными остаётся живой.
2. Удаление сущности, освобождение буферов и повторное использование её слота
   не возвращают старые данные. Event-only сущности очищаются штатным способом.
3. Две разные скриптовые системы могут быть расположены по обе стороны штатной
   системы; ошибка одной отключает только её, как требуют условия первой версии.
4. Round-trip строк, коллекций и ссылок на сущности при сохранении; неверные
   версии и схемы отвергаются до изменения текущего мира.
5. Snapshot между мирами с различными локальными IDs корректно переносит значения
   и ссылки; несовпадающая wire schema отвергается handshake.
6. Отдельный NativeAOT publish минимального хоста, профиль allocations моста и
   время обработки массовой выборки. Указать размеры данных и тёплый/холодный путь.

Эти сценарии пока не выполнены; они определяют проверку будущего дизайна.

## Кандидаты для будущих заметок в docs/knowledge

Следующие короткие выводы можно записать отдельно после подтверждения разработчика:

- Пользовательский пул Dragon не устраняет привязку компонента к CLR типу.
- Динамические модовые данные требуют проверки всей цепочки: запрос, lifecycle,
  сохранение, сеть и инструменты.
- Restart-state план описывает целевую архитектуру, а не текущий бинарный codec API.
- Идентичность скриптовой системы должна отличаться от CLR типа её адаптера.
- Сетевые ссылки на сущности и локальные handles хранилищ требуют разных форматов.

В `docs/knowledge` ничего автоматически не добавлено.
