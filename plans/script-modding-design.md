# Скриптовый моддинг: согласованный дизайн

Дата: 2026-10-06. Статус: решения согласованы в обсуждении; runtime не реализован.

Этот документ уточняет [предыдущие требования](script-modding-requirements.md).
Неизменённые требования сохраняются. При противоречии приоритет имеют решения
ниже: hot reload входит в первую версию, переменные коллекции отложены,
ошибка gameplay-системы останавливает Simulation, исходный layout — SoA.
Работа ведётся по [ExecPlan](script-modding-execplan.md) и
[подробному плану](../docs/superpowers/plans/2026-10-06-script-modding.md).

## Исполнение систем

Используются существующие раннеры. Класс адаптера соответствует нужной фазе,
отдельный экземпляр — зарегистрированной модовой функции. Разделять адаптеры
по backend требуется только при различиях исполнения. Новый scheduler и
отдельный цикл UpdateMods не вводятся.

Регистрация и граф должны различать экземпляры. Type сохраняется как metadata
generated C# descriptors. Стабильное имя системы используется для before/after
и диагностики; числовой индекс узла локален для графа. Порядок и зависимости
строятся при подготовке. Зависимости между разными фазами отвергаются.
Модовые системы первоначально выполняются последовательно. Gameplay использует
fixed dt; остальные функции выполняются в своей фазе. В тике не ищутся имена
функций, не загружаются программы и не строится граф.

## Стороны и объявления

Корневые каталоги мода: Shared, Client, Server. Клиент загружает Shared + Client,
сервер — Shared + Server. Дополнительное поле стороны в системе не требуется.
Состояние сторон раздельно; Shared не означает автоматическую репликацию.
Проверяются доступность сервисов, фаз и целей порядка на каждой стороне.

Компоненты описываются декларативно: стабильное имя, версия, поля и типы.
Системы объявляют ID, фазу, reads/writes, порядок и имя функции. Регистрация
закрывается после подготовки ModSet; изменения проходят через hot reload.
Формат файлов следует выбрать после проверки существующей инфраструктуры.

## Компоненты и доступ

Все компоненты модов публичны внутри ModSet. Другой мод может читать и менять
их через общий API, объявив зависимость и доступ. Схему определяет мод-владелец;
чужие поля нельзя добавлять, для расширения создаётся собственный компонент.
Проверяются обязательные и необязательные зависимости и совместимость схем.

При подготовке разрешаются имена и создаются queries/handles. Queries могут
объединять штатные и модовые компоненты. Данные передаются пачками; мост движка
не создаёт объект или Lua table на каждую сущность. Представления памяти действуют
только в пределах обработки пачки. Handles привязаны к системе, Simulation и
поколению регистрации. Read-handle не позволяет запись. API отклоняет
незаявленный доступ. Сервисы имеют ограничения стороны, фазы и потока.

Создание/удаление сущностей и добавление/удаление компонентов используют заранее
выделенный буфер команд, применяемый в определённых точках pipeline.
Точные точки применения и политика конфликтующих команд требуют проверки.

## Типы и хранение

Поля: целые числа фиксированной разрядности, f32/f64, bool, векторы с явными
полями, ссылки на сущности с поколением, стабильные ID ассетов и ID строк.
Таблица строк принадлежит Simulation. Lua tables, функции, VM objects и
WASM pointers не являются значениями компонентов. Переменные коллекции и
массивы не входят в первый вариант; прежние правила их владения остаются
историей отложенного расширения, а не текущим контрактом.

Модовое storage использует те же entity handles, что DragonECS. На схему —
плотные SoA поля и sparse отображение сущности в индекс. Удаление сущности
очищает модовые данные; поколение защищает от повторного использования слота.
Штатные компоненты доступны через подготовленные bindings к Dragon-пулам.
Query выбирает набор кандидатов и проверяет остальные условия; внутренний
layout и прямые ссылки на пулы модам не выдаются.

Ёмкости готовятся вне тика. Рост памяти выполняется при приостановленной
Simulation; исчерпание буфера не вызывает скрытой аллокации в hot path.
Логическая схема не зависит от layout. Сохранение и сеть кодируют поля,
а не сырые байты памяти. Handles и entity IDs ремапятся при восстановлении
или передаче в другой мир.

## Backend и lifetime

Engine хранит инфраструктуру загрузки/backend. Неизменяемая версия ModSet
содержит зависимости, схемы, определения систем, подготовленные программы
и overrides. Simulation владеет ECS, runtime окружениями, экземплярами систем,
буферами и изменяемыми данными. Две Simulation не разделяют mutable state.

Backend готовит программу, создаёт runtime, привязывает/вызывает функции и
освобождает ресурсы. Общие контракты не содержат Script/DynValue. Первый backend
— Lua; WASM реализуется позже. Backend не владеет авторитетными компонентами.
Для WASM допустимы временные переиспользуемые буферы; копирование и возврат
записей завершаются до возврата системы. Общая физическая память не обязательна.

Первый запуск создаёт initial gameplay state. Reload не повторяет первый запуск:
новая VM восстанавливает привязки к сохранённым компонентам. Globals, closures
и coroutines автоматически не переносятся. Подписки и ресурсы принадлежат runtime
и освобождаются при его уничтожении; миграция схем — отдельная операция.

## Hot reload

Hot reload включён в первый объём, без пересоздания самой Simulation.
Новая версия ModSet/программ, queries и граф готовится до переключения.
Ошибка подготовки оставляет старую версию активной. На границе тика завершаются
системы и применяются команды; затем активируется новая версия целиком.
До успешной активации подготовка/миграции не изменяют старые данные, внешние
эффекты откладываются. После переключения освобождаются старые runtimes,
подписки и ресурсы. Старые handles становятся невалидными.

Совместимые компоненты и сущности сохраняются. Новые схемы допускаются;
изменение существующей схемы требует явной миграции, отсутствие миграции
отклоняет reload. Удаление компонента с живыми данными требует явного правила.
Сетевой reload согласуется между участниками на одном simulation tick;
если согласованное переключение невозможно, reload отклоняется.
Механизм атомарной подготовки и интеграция с DI scopes пока не доказаны.

## Ассеты, сохранения и сеть

Ассеты получают namespace mod-id:asset-name. Override объявляет целевой ID
и замену, сохраняет целевой ID и проверяет тип. Конфликт нескольких замен
требует явного порядка приоритетов; без него загрузка отклоняется. Совпадение
имени файла не заменяет ассет. Итоговая таблица строится до запуска.
При reload новые обращения получают замену; старые ресурсы живут до окончания
использования. Формат приоритетов ещё требуется определить.

Стабильные имена и версии схем используются в сохранениях/совместимости.
Числовые handles локальны для ModSet; hash не заменяет проверку уникальности.
При несовместимом сохранении выполняется явная миграция либо загрузка отменяется;
миграции reload обязательны для принятия изменённой схемы, произвольные миграции
старых save-файлов не добавляются автоматически в первый объём.

Синхронизируемые поля явно отмечаются, используется общий сетевой pipeline.
Handshake проверяет обязательный gameplay-набор и wire schemas, косметические
клиентские моды не обязаны совпадать, если не влияют на Simulation/протокол.
Сервер авторитетен и проверяет команды клиента.

## Ошибки и лимиты

Обязательного бюджета инструкций/времени нет. Ограничение можно включить
для сервера/диагностики, только если выбранный backend поддерживает его.
Безлимитный callback может задержать тик или зависнуть; гарантии длительности
тика для произвольного мода нет. Не следует обещать работающую отмену Lua
без проверки. Если прерывание невозможно, остановка worker — путь восстановления.

Ограничения памяти VM и ёмкости буферов остаются отдельным контрактом.
Ошибка gameplay-системы останавливает Simulation с ID мода, системы, фазы
и причиной: автоматического отката частично записанных компонентов нет.
Runtime-ошибка не обещает бесшовное продолжение после reload. Файлы, сеть,
процессы доступны только через явно предоставленный Mod API.

## Критерии первого варианта

Две функции одного типа адаптера располагаются по разные стороны штатной
системы; незаявленный доступ отклоняется; межмодовой компонент используется
без копии; удалённый entity handle не видит новый слот. Проверяются повторные
reload, ошибочная программа и миграция, отсутствие повторного initial spawn
и подписок, две независимые Simulation, сохранение/сеть со сменой локальных IDs,
совместимость gameplay-набора и согласованный сетевой reload.

Измеряются allocations моста и VM отдельно, время пачек, объём и пик памяти
reload. Проверка бесконечного цикла выполняется только в изолированном worker
с внешним watchdog; в режиме без бюджета автоматическое прерывание не требуется.
