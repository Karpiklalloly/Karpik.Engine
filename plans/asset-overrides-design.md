# Asset overrides при запуске

- Status: ready
- Started: 2026-11-19
- Updated: 2026-11-19
- Revision: 16
- Complexity: complex (auto: обнаружение модов, порядок подготовки Engine/ModSet и публикация Content snapshot)

## Goal and scope

Подтверждённый сценарий: игрок кладёт готовый мод в `Mods`, запускает игру и видит заменённую текстуру; конфиг/код игры менять не нужно. Замена явная, игровой ассет сохраняет стабильный ID. Выбор замен выполняется при запуске, фактическая загрузка payload может остаться ленивой. Штатный reload базового Content сохраняет подмены из текущего опубликованного набора модовых пакетов. Разработчик расширил срез: нужен механизм обновления модового контента во время работы игры; способ обнаружения не задан. Refresh меняет только ассеты и декларации; можно подключать, обновлять и удалять чисто контентные пакеты. Активный Lua ModSet, VM, схемы и ECS не меняются. Миграции, сохранения, сеть и запуск/выгрузка Lua-модов в этот срез не входят.

## Requirements and behavior

Общий дизайн моддинга (`git show codex/modding-0.7:plans/script-modding-design.md`, раздел «Ассеты, сохранения и сеть») задаёт явную пару target/replacement и совместимость типов. Имя файла не является идентификатором замены. Для этого среза приоритет определяется штатной очередью загрузки: среди модов, которые заменяют один ID, побеждает последний в этой очереди. Неверный ID или несовместимый тип не останавливает запуск: невалидная замена пропускается, ошибка попадает в лог (D7).

## Architecture and integration

На `main` (`d8ee920`) `ContentRegistry` является Engine singleton; `Start` загружает manifest, а `RegisterManifest` однократно публикует root со слотами первого поколения. `ContentManifestEntry` содержит `AssetId`, declared type, locator, hashes и зависимости. [ADR Content snapshots](../docs/02_ADR/content-runtime-snapshots.md) закрепляет immutable root и version-bound refs. В `codex/modding-0.7` реализована ModSet preparation, которой нет на `main`. По явному решению разработчика `codex/asset-overrides` переведена fast-forward на базу `codex/modding-0.7` (`03f2ead`) для использования существующего обнаружения модов. Родительская ветка не менялась. Зависимый PR сначала должен целиться в `codex/modding-0.7`; после слияния родителя — перенаправить на `main` и проверить, что diff не содержит унаследованных изменений.

На базе `03f2ead` и Static, и Dynamic регистрируют `ContentRegistry` как `IStartable`; Engine container строится до ModSet, а mod scan ждут до создания Simulation (`Runner.cs`). `AssetsManager` при чтении `mod_info.json` сначала использует обычный файл, но legacy-путь для других ассетов может обратиться к Content по имени и закэшировать payload. Поэтому нельзя публиковать подмены поверх уже выданных generation-1 ссылок без смены контракта; предпочтительно явное завершение startup Content после scan и до первого игрового потребителя, сохраняя независимый путь чтения метаданных. В `ContentRegistry.PrepareCoreAsync` существующий Content reload строит кандидат из входящего manifest, а не из объединённого каталога: без явной политики он удалит модовые записи и перетрёт подмены. `ContentSlot` уже удерживает собственный store; не нужен lookup по модам на чтении.

### Проверка исходников

- Ранний потребитель подтверждён: `OpenGLGraphicsBackend.Start()` вызывает `Preset2DPipeline.Init()`, который через `AssetsManager` загружает базовые шейдеры по пути. При наличии только манифеста этот путь требует базового индекса уже при старте Engine. `MergeThread` принимает ссылку на реестр для порядка освобождения, а не для ранней загрузки по ID. Нельзя целиком отложить инициализацию Content до ModSet.
- Рекомендуемая граница: при старте Engine готов только исходный индекс по имени; после штатного `IModSetPreparation` и до создания Simulation публикуется первый каталог по ID (generation 1). Не публиковать исходные ID временно и не превращать startup в обычный reload: ранние refs и уже загруженные payload имели бы другой контракт. Reload endpoint должен принимать работу лишь после итоговой публикации. Сохраняем один реестр и прежнее владение графики.
- `ContentReloadCoordinator` готовит кандидата холодно и считает изменения по ID-слотам. Вариант с независимыми базовым индексом и ID-слотами в одном root нужен также при изменении только скрытого оригинала: обновить базовый индекс и его store атомарно, не меняя эффективные ID-слоты, их версии и уведомления. Не считать такой reload полным no-op только по равенству effective entries. При смене фактического источника слота проверять происхождение/store, а не только равенство полей манифеста.
- `GenerationContentStore.OpenCurrent` фиксирует конкретное поколение и удерживает его через OS claim; протокол требует записи в output root. Проверка read-only projection не удерживает поколение и не защищает от параллельного publish. Пропускать незахваченные папки как будто они immutable нельзя. Вариант без копирования годился для startup-only, но заменён локальным захватом D12 из-за удаления пакетов в live refresh. Content registry удерживает принятый источник независимо от текущих победителей; исходные и кандидатные слоты удерживают собственное владение. Runner освобождает ModSet раньше Engine, поэтому ссылкой из ModSet без отдельного владения реестра пользоваться при retirement нельзя.

## Constraints

Не добавлять overlay lookup, аллокации, блокировки или I/O в обычные runtime reads. Решить конфликты и собрать итоговый набор до публикации; не делать второй registry без доказанной необходимости. Не допустить незаметной потери startup overrides на существующем Content reload. Для пакетов проверить валидность provenance, locator/store, target side и зависимости до принятия архитектуры. Не менять формат фиксированных refs без отдельного обоснования.

## Decisions and alternatives

- D1 — граница первого результата: **автоматический подхват из `Mods` при запуске** (выбор разработчика). Явное подключение пакетов приложением проще опубликовать независимо, но не выполняет заданный сценарий. Использовать существующее обнаружение как предпочтительную интеграцию, не заводить независимый второй обход.
- D2 — применение: предпочтительна предварительная композиция до единственной публикации, а не второй lookup при каждом resolve. Офлайн-композиция с пересборкой игры не выполняет D1. Размещение этапа композиции остаётся открытым.
- D3 — приоритет: **последний мод в штатной очереди побеждает** (выбор разработчика). Источник — итоговый детерминированный порядок загрузчика, не обход папок, не время завершения I/O и не отдельные приоритеты ассетов. В ветке моддинга `ModsRegistry.Scan` сейчас публикует каталог с `StringComparer.Ordinal` по ID. Не вводить отдельный механизм приоритетов в этой задаче: числовые приоритеты модов подвержены коллизиям, а ручной выбор по каждому ассету дублирует очередь.

- D4 — цели: **базовые ассеты и ассеты других модов** (выбор разработчика). Вариант «только базовые» избегает отсутствующих владельцев, но не позволяет выпускать отдельные визуальные патчи к модам. Предпочтительная семантика — проверить цели по полному набору исходных деклараций, затем применить D3, не превращая порядок в требование «владелец объявлен раньше». Порядок определяет победителя, а не видимость ID. Замены не транзитивны (D6).

- D5 — отсутствующий владелец: **пропустить только эту замену и предупредить** (выбор разработчика). Если владелец установлен, а исходный целевой ассет отсутствует, это ошибка декларации. Отличать отсутствие владельца от отсутствия ID по явной идентичности владельца; неизвестный игровой ID — ошибка. Вариант «всегда ошибка» мешает опциональным визуальным патчам; «всегда пропуск» скрывает опечатки и несовместимые обновления. Ошибка не блокирует запуск (D7).

- D6 — цепочки: **замены не транзитивны** (выбор разработчика). Берём исходный payload явно указанного ассета, а не результат разрешения его ID после подмен. Если `A:icon ← B:icon` и `B:icon ← C:icon`, для A используются исходные байты B, для B — исходные байты C. Транзитивные алиасы позволяют неявно изменить больше целей и требуют обхода цепочек/проверки циклов; не вводим их. Это не отменяет проверку обычных зависимостей content manifest.

- D7 — невалидная замена: **пропуск с логом, без остановки запуска** (выбор разработчика). Для ошибки отдельной записи (например, неверный ID или несовместимый тип) пропускается запись, а не скрипты мода и не валидные замены. Она не вытесняет предыдущую валидную замену; при её отсутствии остаётся оригинал. Вариант fail-fast не выбран: необязательный визуальный патч не должен блокировать старт. Фатальные ошибки базового Content и инфраструктуры не маскируются.

- D8 — **штатный hot reload базового Content сохраняет модовые подмены уже в первом срезе** (выбор разработчика). Отключение endpoint проще, но ломает editor workflow. Подготовка каждого reload объединяет входящий базовый manifest с теми же зафиксированными модовыми пакетами и правилами; сравнение, версии и уведомления отражают итоговый каталог, а публикация остаётся на штатной границе. Если эффективный ассет по-прежнему указывает на те же данные мода, изменение скрытого оригинала не инвалидирует ссылку и не даёт ложного уведомления. Предлагаемая реакция на исчезновение целевого ID при базовом reload: D7, лог и пропуск подмены, а не сохранение удалённого базового ID; при повторном появлении цель снова валидируется. Отказ подготовки сохраняет последнюю рабочую версию каталога. Запрос базового reload сам по себе не воспроизводит scan и не меняет модовые пакеты. Отдельный запрос обновления модов обсуждается в Q5; оба вида публикации должны иметь общий порядок, чтобы один не затирал результат другого.

- D9 — доставка: **автор собирает готовые пакеты существующим Content CLI до публикации** (согласовано разработчиком). `content create` создаёт `.meta` с собственным ID, `content build` собирает собственные ассеты мода под нужную сторону; внешние цели указываются отдельно в метаданных мода. Игрок копирует папку в `Mods`, игра читает готовый пакет, не вызывает CLI и не обрабатывает исходники заново. Отдельную команду упаковки не вводим. Loose-исходники упростили бы самый первый патч, но потребовали бы второго runtime-пути валидации и обработки.

- D10 — публичный охват: **подмены только через стабильный `AssetId` в Content registry** (выбор разработчика), в том числе через generated refs/live bindings. Старый `AssetsManager` и прямые файловые чтения продолжают видеть базовые данные. Поиск `TryOpenArtifact`/`TryResolveArtifact` по имени уже использует snapshot, поэтому его индекс должен остаться привязан к исходным базовым дескрипторам, а не к модифицированным ID-слотам; оба представления публикуются вместе, отдельного registry и второго lookup в ID-пути не нужно. Альтернатива — переопределять также legacy-пути, но она требует нового порядка приоритетов loose-файлов и правил инвалидации legacy-кэша.

- D11 — **явный live refresh модового Content без смены Lua ModSet** (согласовано разработчиком). Запрос «Обновить контент модов» запускает разовую проверку `Mods` вне кадрового потока, подготовку кандидата и атомарное переключение на существующей границе Content. Скрипты, VM, scheduler и ECS не переключаются; из новых пакетов допускаются только чисто контентные. Сигнал с известным путём/поколением мог бы исключить обход, но не покрывает ручное копирование; watcher и периодический polling не нужны. `ModsRegistry.Scan` сейчас одноразовый и фиксирует ModSet; существующий Lua reload меняет только код при прежних определениях. Не запускать повторный Scan активного Lua ModSet.
- D12 — **локальный захват пакетов и один cold-путь публикации**. Движок потоково копирует только объявленные cooked-файлы в закрытую для модов рабочую папку процесса вне `Mods`; повторный refresh переиспользует совпадающее поколение и декларацию. OS claim на исходную папку не удерживает файлы после ручного удаления; полная загрузка в RAM нарушает предсказуемость памяти. Исходные папки могут быть read-only. Сверять маркер/манифест и байты декларации до и после захвата, отклонять отсутствующие/необычные файлы, ссылки, выход за корень и несоответствие размера; издатель не меняет артефакты опубликованного поколения на месте. Это проверка согласованности обычной установки, не криптографическая подпись или защита от другого процесса с теми же правами. Действуют `MaximumAssets=4096` для эффективного каталога, до 4 MiB на каждый манифест/декларацию и не более 4 GiB суммарно в рабочей папке процесса, включая staging/retirement; превышение диагностируется до публикации. Кандидат не виден до захвата и проверки; незавершённые копии очищаются при ошибке, опубликованные — только после освобождения последнего владельца (active/candidate/retired roots, слоты, чтения). При shutdown сначала остановить приём обновлений, прервать/дождаться подготовки и вывести графику из использования старых данных, затем освобождать store. Не удалять чужие рабочие папки. Один coordinator сериализует базовый reload и модовый refresh, каждый берёт последний опубликованный второй слой. Повторный одновременно ожидающий refresh получает Busy; существующая семантика supersede для базовых запросов сохраняется, операции разных видов не вытесняют друг друга.
- D13 — **контракт пакета**. `Mods/<папка>/mod_info.json` по-прежнему задаёт ID; новый необязательный `contentOnly: true` явно отмечает пакет без Lua entry points (не запускать Lua для него; при противоречии — отклонить с диагностикой). Существующие моды без флага совместимы. На каждой стороне читается только `Content/Client` или `Content/Server`; в ней используется текущее поколение существующего `content build`, namespace равен ID мода. `overrides.json` в той же папке — опциональная декларация v1 с `schemaVersion`, `generationId` и `overrides`: каждая запись содержит `targetModId` (null для игры), `targetAssetId`, `replacementAssetId` из собственного исходного manifest. Декларация должна соответствовать поколению: автор готовит пакет до помещения в `Mods`, при обновлении публикует декларацию целиком, а переходное несоответствие отклоняется и можно повторить refresh. JSON без executable hooks; не связывать внешний ID с графом сборки. Альтернативы — хранить правила в общем `mod_info.json` (хуже привязка к стороне и поколению) или менять формат Content CLI (лишний новый формат). Обычные зависимости пакета локальны, сравнивается точный `DeclaredType`; ошибка отдельной подмены, в том числе вносящей цикл в итоговый граф, пропускается по D7 в детерминированном порядке. Пакет с невалидным manifest или конфликтом собственного ID не сливается частично: при старте пропустить такой пакет с диагностикой; при refresh отклонить кандидат. Базовые ID имеют преимущество, конфликт между модовыми собственными ID не является override и диагностируется; при старте сохранить первый валидный пакет в штатном порядке. Дубликаты ID мода не выбирать по порядку обхода: такие пакеты конфликтуют и исключаются из Content при старте либо отклоняют refresh.
- D14 — **старт и запрос**. Сохраняем ранний доступ к базовым путям; финализируем ID-каталог перед Simulation после подготовки ModSet, с базой v1. Явный асинхронный локальный host API обновления (для меню/консоли игры) без нового IPC, UI и таймера, на Client и Server независимо. На refresh активный Lua ModSet фиксирован: новые или удалённые Lua-моды требуют перезапуска, для уже активных разрешено только обновление их cooked-слоя; исчезновение папки активного Lua-мода сохраняет последний захваченный слой и сообщает о перезапуске. Отсутствие ранее принятого content-only пакета означает удаление, но нечитаемая/частично скопированная папка не означает удаление. Для определения кандидатов используется один общий алгоритм discovery, а не повторная мутация `ModsRegistry`. Обычные ID refs остаются привязаны к версии, живые bindings получают обновление штатно. Сетевой согласованный refresh не вводится.

## Acceptance criteria (черновик)

- AC1 — готовый мод в `Mods` обнаруживается при старте без правок конфига игры, и по прежнему ID и совместимому типу загружается replacement; без мода загружается оригинал.
- AC2 — при двух валидных заменах одного ID побеждает последняя по штатной очереди загрузки; порядок обхода диска не влияет на результат.
- AC3 — чтение использует существующий путь, без дополнительного lookup или per-read allocations.
- AC4 — неверная цель или несовместимый тип логируются с ID цели и источником декларации; старт продолжается, предыдущая валидная замена или оригинал сохраняется.
- AC5 — базовый reload обновляет открытые базовые ассеты без пересканирования модов, сохраняя модовые ID и неизменившиеся выигравшие подмены вместе с их версиями. Уведомления отражают только реальные изменения итогового каталога. Неуспешный кандидат оставляет прежний каталог.
- AC6 — модовые пакеты выпускаются независимо от комбинации у игрока. Одни и те же пакеты устанавливаются по отдельности или вместе без пересборки. Декларация внешней цели не требует включать её байты или манифест в build мода; цель и победитель проверяются при композиции реально загруженного набора.
- AC7 — явный refresh добавляет, обновляет и удаляет content-only пакет без перезапуска Simulation или Lua. Неудачное чтение не меняет активный каталог; ранее принятые ленивые чтения сохраняют источник до retirement. Базовый reload и refresh не теряют результаты друг друга.

- AC8 — исходная папка может быть read-only; удаление папки не ломает незагруженный ранее ассет старого активного каталога до commit. Повреждённый, неполный, выходящий за корень или слишком большой пакет не публикуется. Копии abort и retired очищаются без преждевременного освобождения активных/захваченных чтений.
- AC9 — ранние базовые шейдеры и весь legacy-путь видят оригинал; первый ID-каталог содержит подмены в поколении 1. Client и Server принимают только своё поколение; no-mod hosts и Static/Dynamic сохраняют поведение.
