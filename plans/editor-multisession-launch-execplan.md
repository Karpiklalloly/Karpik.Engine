# Добавить запуск сервера и нескольких клиентов из редактора

Этот ExecPlan — живой документ. Его необходимо поддерживать по правилам `plans/PLANS.md`.

## Purpose / Big Picture

После выполнения плана разработчик сможет из `Karpik.Editor` запустить один сервер, затем несколько независимых клиентов, увидеть все процессы в панели «Сессии» и управлять каждым из них отдельно. Сервер является родительской сессией: пока он не запущен, клиенты недоступны; остановка или аварийное завершение сервера останавливает все клиенты.

Выбор строки «Сервер», «Клиент 1», «Клиент 2» и так далее определяет единственный источник ECS snapshot. «Иерархия» и «Инспектор» показывают только сущности и компоненты выбранного backend-процесса и не смешивают состояния разных миров.

## Surprises & Discoveries

- Observation: `Karpik.Editor` сейчас является client composition root (`IsClient=true`), поэтому его output содержит client-модули и не может корректно запустить сервер только посредством `--side=Server`.
  Evidence: `Karpik.Editor/Karpik.Editor.csproj` импортирует `AutoGenerated.targets`, а server `PluginReference` в этом target имеет условие `IsServer=true`.
- Observation: `Karpik.Engine.Core.Runner` уже принимает `--side`, но конкретный состав модулей определяется рабочим каталогом и созданным `Plugins.targets` каталогом `modules.version.*`.
  Evidence: `Karpik.Engine.Core/ProcessManagement/ProcessManager.cs` передаёт `--side`; `Plugins.targets` создаёт side-specific staging directory и файл `.complete`.
- Observation: текущий `EditorShellViewModel` владеет ровно одним `EditorPreviewController` и опрашивает его snapshot не чаще 4 Hz.
  Evidence: `Karpik.Editor/ViewModels/EditorShellViewModel.cs` содержит одно поле `_previewController` и один `PollSnapshotsAsync`.
- Observation: launcher output хранит несколько исторических `modules.version.*`; worker выбирает последний завершённый каталог, а bundle packaging обязан исключать root-файлы модулей противоположной стороны.
  Evidence: проверка собранных `runtimes/client` и `runtimes/server` обнаружила исторические staging-каталоги, но side marker и root module DLL после фильтрации остались side-pure.
- Observation: `WorkerReady` отправлялся до выполнения отложенного bootstrap `Setup`, поэтому состояние `Running` не означало готовность ECS и модулей.
  Evidence: multi-session integration получал ready, пока stdout ещё содержал `On Configure`; выполнение scheduler setup до сигнала устранило гонку.
- Observation: клиент выбирал свободный UDP-порт через отдельный probe socket, что создавало TOCTOU-гонку между несколькими процессами.
  Evidence: сервер видел только одно подключение из двух; переход на атомарный `LiteNetLib.NetManager.Start()` на доступном порту дал два подтверждённых подключения.
- Observation: client snapshot нельзя обслуживать через render/main scheduler: первый occluded SDL/Veldrid client может блокироваться в render, а ECS принадлежит simulation thread.
  Evidence: один из двух клиентов стабильно не отвечал на snapshot; редкая очередь работ на `ClientSimulationWorker` сохранила обычный frame path без аллокаций и восстановила ответы обоих клиентов.

## Decision Log

- Decision: использовать два физически раздельных runtime-пакета `runtimes/server` и `runtimes/client`, собранных существующими `ServerLauncher` и `ClientLauncher` composition roots.
  Rationale: это сохраняет строгую границу Client/Server и повторно использует существующий список модулей без создания третьих host-проектов.
  Date/Author: 2026-07-14 / Artem and Codex
- Decision: редактор перестаёт быть client composition root и становится только desktop orchestrator.
  Rationale: UI не должен неявно владеть игровыми client-модулями; каждый backend запускается из собственного runtime-пакета.
  Date/Author: 2026-07-14 / Artem and Codex
- Decision: orchestration model содержит не более одного сервера и произвольное число явно созданных клиентских сессий.
  Rationale: это соответствует локальному multiplayer workflow «сервер, затем несколько клиентов» и позволяет адресно останавливать и перезапускать процессы.
  Date/Author: 2026-07-14 / Artem and Codex
- Decision: сервер является родительской сессией; его stop, restart или fault каскадно останавливает клиентов, но после нового старта сервера клиенты автоматически не восстанавливаются.
  Rationale: клиенты не должны оставаться подключёнными к несуществующему authority, а автоматическое восстановление могло бы неожиданно породить процессы и скрыть ошибки старта.
  Date/Author: 2026-07-14 / Artem and Codex
- Decision: snapshot polling выполняется только для выбранной работающей сессии; результат запроса от прежнего выбора отбрасывается.
  Rationale: сущности разных ECS worlds нельзя смешивать, а параллельный polling всех процессов создаёт ненужные IPC-запросы и аллокации.
  Date/Author: 2026-07-14 / Artem and Codex
- Decision: client editor snapshot выполняется на simulation thread через отдельную редкую work queue, а server snapshot остаётся на server/main tick thread.
  Rationale: это синхронизирует обход ECS с владельцем gameplay state и не связывает inspection с потенциально блокирующим render; обычный кадр не создаёт managed allocations.
  Date/Author: 2026-07-14 / Codex

## Outcomes & Retrospective

Основная реализация завершена. Editor стал side-neutral orchestrator, собирает два runtime-пакета, управляет одним сервером и произвольным списком клиентов и показывает ECS только выбранной сессии. Интеграционный сценарий подтвердил три разных PID, ответы snapshot каждого backend, два реальных подключения к серверу и каскадную остановку.

В ходе end-to-end проверки были исправлены две скрытые runtime-гонки: преждевременный `WorkerReady` и неатомарный выбор клиентского UDP-порта. Дополнительно client snapshot перенесён с потенциально блокирующего render/main thread на simulation thread.

Независимое ревью дополнительно выявило и помогло закрыть гонку резервирования simulation frame, частичный cascade shutdown, гонку публикации состояния `Running`, остановку snapshot polling после единичной ошибки и падение IPC на исключении component getter. Публикация runtime-пакетов теперь атомарна: новый пакет сначала полностью собирается и проверяется в staging-каталоге, затем заменяет рабочий каталог с rollback при неудаче.

Финальные результаты: `Karpik.Engine.Core.Runner.Tests` — 43/43; `Karpik.Editor.Tests` — 26/26; opt-in multi-session integration — 1/1 с двумя подтверждёнными server connections; editor bundle build и desktop smoke прошли; после teardown процессов `Karpik.Editor`/`Karpik.Engine.Core.Runner` не осталось. Повреждённые Dock-пропорции покрыты тремя регрессионными тестами и визуальной проверкой на реальном workspace с `LeftPanelWidth = 0`. Отображение `Context` leaf-вкладок покрыто отдельным регрессионным тестом; повторный desktop smoke показал в панели «Сессии» запущенный сервер с PID и 17 сущностями выбранного backend. В build сохраняются существующие package/compiler warnings, включая известный `Newtonsoft.Json 9.0.1` advisory; новых ошибок сборки нет.

## Context and Orientation

`Karpik.Engine.Core/Editor/EditorPreviewController.cs` является публичной lifecycle-обёрткой над внутренним `ProcessManager`. Сейчас конструктор всегда создаёт `ProcessManager` с `Side.Client`, поэтому controller требуется сделать side-aware и открыть read-only PID процесса.

`Karpik.Engine.Core/ProcessManagement/ProcessManager.cs` запускает `Karpik.Engine.Core.Runner`, создаёт уникальный named pipe, ждёт `WorkerReady`, получает stdout/stderr, запрашивает editor snapshot и выполняет graceful shutdown. Один экземпляр `ProcessManager` обслуживает один worker; для нескольких клиентов нужны независимые controller instances с разными pipe names.

`ClientLauncher/ClientLauncher.csproj` и `ServerLauncher/ServerLauncher.csproj` — существующие composition roots. Их `IsClient`/`IsServer` properties управляют условными `PluginReference` из `AutoGenerated.targets`. `Plugins.targets` собирает модули и размещает их в `modules.version.<guid>` рядом с executable. Editor build должен использовать эти launcher-проекты для формирования двух каталогов, но не добавлять ссылки на их assemblies в UI.

`Karpik.Editor/ViewModels/EditorShellViewModel.cs` сейчас содержит команды единственного preview, общий статус, один snapshot loop и view-models иерархии/инспектора. `Karpik.Editor/Docking/EditorDockFactory.cs` создаёт панели «Проект», «Иерархия», «Инспектор», «Консоль» и документ «Предпросмотр». Новый `SessionsViewModel` станет отдельной dock-панелью «Сессии».

Термин «runtime-пакет» в этом плане означает отдельный каталог с `Karpik.Engine.Core.Runner`, его managed/native dependencies, одним или несколькими завершёнными `modules.version.*` и side marker. Термин «активная сессия» означает выбранную пользователем строку, а не просто последний запущенный процесс.

## Real-Time Assessment

Изменения не входят в `Update`, `FixedUpdate`, ECS `Run`, сетевой pump или render loop. Создание view-models, процессов, строк логов и cancellation objects выполняется только по пользовательским командам или редким lifecycle events. Общая консоль остаётся ограниченной 2,000 строками.

Snapshot продолжает аллоцировать debug DTO и JSON, но только для одной выбранной сессии и не чаще 4 Hz. При переключении увеличивается generation token; завершившийся запрос применяет результат только при совпадении session id и generation. Это предотвращает отображение устаревшего мира без запуска polling для всех backend-процессов.

Side boundary усиливается: `Karpik.Editor` больше не импортирует client/server plugins; client bundle создаётся только `ClientLauncher`, server bundle — только `ServerLauncher`. Ни один Client project не импортируется в Server и наоборот. Tick/fixed-dt поведение runtime не меняется.

Lifecycle operations сериализуются одним асинхронным gate в session manager. Server exit callback не должен блокировать process event thread: он ставит каскадную остановку, а повторные stop/fault события должны быть идемпотентными. Каждый controller владеет собственным pipe и disposable resources.

## Idempotence and Recovery

Build/test команды безопасны для повтора. Runtime bundle target должен создавать пакеты во временных каталогах внутри `$(TargetDir)` и заменять итоговые `runtimes/client` и `runtimes/server` только после успешного launcher build; не оставлять частично обновлённый side marker. Если один launcher build неуспешен, editor build завершается ошибкой и сохраняет последний целый пакет либо не создаёт пакет вообще.

`StopAsync`, cascade stop, `StopAllAsync` и `Dispose` должны быть идемпотентными. Integration teardown всегда пытается завершить весь process tree. Для rollback удалить только новые editor orchestration/target files и вернуть editor project к прежним imports через обычный patch; не применять `git reset --hard` и не затрагивать пользовательские `.obsidian` или несвязанные dirty files.
