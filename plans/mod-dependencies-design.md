# Зависимости модов в Modding 0.7

- Status: ready
- Started: 2026-11-23
- Updated: 2026-11-23
- Revision: 4
- Complexity: complex (auto: публичный формат, единый порядок startup/Lua/Content и транзакционная граница refresh)
- Development mode: strict-tdd (явный выбор разработчика)
- Branch: `codex/mod-dependencies` от `codex/modding-0.7` (`be5ddad`). Первоначальный PR в родителя с явного разрешения разработчика; `main` не трогать.

## Goal and scope

Автор объявляет зависимости мода; хост валидирует ModSet и готовит порядок до Lua startup и публикации первого ID-каталога. Тот же контракт проверяется при явном Content refresh. Демо отложено до общей проверки удобства API и работоспособности. Полная смена Lua ModSet, миграции ECS, сеть, сохранения, установка пакетов и новый UI вне задачи.

## Requirements and behavior

- Shared-ограничения применяются на обеих сторонах, side-ограничения — только на своей. Отсутствующая обязательная цель, несовместимая доступная версия (включая optional) и цикл с присутствующими optional отклоняют весь ModSet. Отсутствующая optional цель не добавляет ребро. Направление порядка: цель до зависимого мода.
- Последний валидный override одного AssetId в штатном порядке побеждает ([D3 asset overrides](asset-overrides-design.md#L38)). Это порядок модов и lifecycle, а не неявная зависимость между Update-системами: правила scheduler не меняются. Reverse cleanup использует существующий обратный порядок.
- Ошибка при старте не разрешает запуск отдельных Lua VM или публикацию частичного ID-каталога. На refresh отказ сохраняет последний принятый Content и неизменный Lua-набор.

## Architecture and integration

Действующий `ModsRegistry` сортирует discovery-проекции по ordinal ID; `LuaSimulationPreparation` сортирует повторно и сохраняет список для code reload; `LuaModContentRefresh` независимо сортирует Content по ID. Один общий cold-резолвер рассчитывает порядок, проекции Lua и Content потребляют его без повторной сортировки. Code-only reload использует неизменяемый startup Lua-порядок и результаты разрешения, не пересканирует metadata. `ContentComposition` продолжает владеть проверкой собственных AssetId и составом принятых пакетов; списки модов не заменяют граф ассетов или scheduler graph.

Startup использует уникальные discovery-определения в качестве источников деклараций, в том числе при отсутствии payload на стороне; Shared не становится Client-only из-за расположения файлов. Цель доступна только по D4. Для графа наличие успешно захваченного cooked-пакета предварительно означает доступность; если такой пакет был использован в графе (источник с активными обязательствами либо разрешённая цель), но `ContentComposition` его отклонил и нет Lua entry point, весь startup отклоняется до публикации. Не выполнять пересортировку после отбрасывания пакетов: это может сменить победителя при конфликте ID или override. Если реестр Content не подключён, граф Lua-only использует те же правила без cooked-провайдеров. Уже существующие legacy warnings и допуск несвязанных с графом некорректных Content-пакетов не подменяют отказ графа.

Refresh строит кандидат из замороженных startup Lua-определений (включая version, разрешённые цели и side-eligibility) и действительно выбранных live content-only изменений. Пересканированные скриптовые манифесты не могут подменить active Lua identity/версию/декларации. Metadata ранее принятого content-only пакета, который удерживается по правилу restart-required, следует за его опубликованным пакетом, а не за нынешним содержимым папки. Версия/декларации кандидата публикуются вместе с соответствующим Content, в том числе при неизменных cooked bytes; отказ или отмена не меняют метаданные предыдущего. Упорядочить выбранные пакеты по кандидату, сравнить относительный порядок всей активной Lua-проекции и наборы `has_dependency` с зафиксированными значениями. Та же граница отмены, владения захватами и атомарной публикации, что и сейчас. Базовый Content reload сохраняет порядок и состояние принятых модовых пакетов без rescan.

## Constraints

Нет новых аллокаций, графового поиска, locks или I/O в обычном Update/FixedUpdate, чтении ассетов либо кадровой публикации. Lua-проверка по явному вызову читает заранее подготовленный неизменяемый набор точным ordinal lookup, без новой аллокации со стороны bridge на вызов; Lua VM overhead отдельно и не обещает zero-GC произвольного скрипта. Cold input проверять на существующих границах объёма metadata; обход графа без неограниченной рекурсии. Не добавлять Content Runtime → Modding, зависимость между Client и Server или отдельный координатор.

## Decisions and alternatives

- D1 — **зависимости модов, без демки** (разработчик). Демка позже подтвердит сквозной сценарий и удобство API. Подтверждены strict TDD и отдельная зависимая ветка.
- D2 — **валидировать Content refresh поверх замороженного Lua** (разработчик); нарушение графа или смена порядка активного Lua отклоняют refresh. Альтернатива — требовать restart при любом изменении графа: проще, но урезает установленное поведение content-only refresh. Пересобирать Lua VM нельзя.
- D3 — **числовой `MAJOR.MINOR.PATCH`** (разработчик); необязательные `minVersion` включительно, `maxVersionExclusive` исключительно, оба отсутствуют — любое значение. Ровно три неотрицательные десятичные компоненты в диапазоне `Int32`; сравнение числовое. Неупорядоченный/пустой объявленный интервал — ошибка. Старая произвольная строка `version` сохраняется без сравнения; если на неё наложено ограничение, неприводимая версия несовместима. SemVer с prerelease и отдельной зависимостью не нужен для среза.
- D4 — **цель реально доступна на текущей стороне** (разработчик): Shared/side Lua entry point, распознаваемый штатным loader, либо допущенный cooked-пакет. Одна папка/manifest без payload недостаточна; для Lua наличие entry point не подменяет обычную проверку кода. Если подходящий cooked payload присутствует, но повреждён или отвергнут, он не выдаётся за отсутствующий при проверке зависимости; при отсутствии подходящего Lua entry point объявленная ссылка на такой target отклоняется, включая optional. Отсутствие payload текущей стороны, напротив, считается отсутствием цели. Привязка к installed owners проще, но даёт ложное разрешение в другой стороне и смешивает контракт с диагностикой override-target.
- D5 — **`has_dependency(id)` в Lua** (разработчик). С начала top-level на Shared и активной стороне функция принимает один строковый ID и сообщает, была ли успешно разрешена прямая активная декларация своего мода. Для неизвестной, транзитивной, иной стороны или отсутствующей optional цели возвращает `false`, не раскрывая список установок. Неверный тип/число аргументов — ошибка Lua API. Это факт разрешения, не enabled-state или готовность runtime; функции соседей не экспортируются. Если Content refresh изменил бы результат в активном Lua, отклонить его с restart-required. Live lookup проще синхронизировать с Content, но потенциально меняет решение уже выполненного Lua top-level/on_load; выбран frozen snapshot. Сравнивается доступность прямых целей, а не новая версия сама по себе (совместимое изменение Content допустимо).
- D6 — **любые найденные дубликаты mod ID отклоняют весь ModSet** (разработчик). Точное ordinal сравнение. Это намеренно заменяет legacy fallback «первая папка» даже для модов вне графа; refresh и раньше отклонял неоднозначность. Альтернатива — оставить fallback у нереференсируемых модов: меньше миграций, но неодинаковая идентичность и неожиданный отказ при добавлении зависимости.
- D7 — формат и слияние: необязательный объект `dependencies` в `mod_info.json` с ключами `shared`, `client`, `server`; значение — массив записей с `id`, необязательным boolean `optional` (по умолчанию `false`) и границами D3. Пропуск секции равен пустой секции, явный `null` и неверные типы/поля нового контракта невалидны. Повтор ID внутри группы и самозависимость недопустимы. Один ID в Shared и активной стороне проверяется по обеим декларациям: нужна цель, если хотя бы одна обязательна; должны выполняться обе границы; ребро одно. Side override общей записи мог бы ослабить глобальное ограничение; запрет любых пересечений не позволил бы уточнять диапазон по стороне. Разнесение по отдельным файлам дублировало бы discover/refresh источники. Валидировать форму всех секций, даже неактивной, но не проверять наличие/версии/циклы её целей; явная ошибка формата `dependencies` фатальна, старые unrelated discovery warnings сохраняют прежний startup-режим.
- D8 — **детерминированная топосортировка с ordinal ID среди готовых узлов**. При отсутствии рёбер сохраняется старый порядок. Обход папок непредсказуем, ручной приоритет дублирует порядок, DFS по отсортированным входам может инвертировать привычный порядок независимых готовых узлов. Диагностика показывает конкретный путь цикла или хотя бы его циклическое подмножество без downstream узлов.
- D9 — состояние и публикация: валидировать факт приёма cooked-провайдеров в cold startup до первой публикации; отдельное повторное чтение файлов или повторный независимый resolver acceptance рискуют разойтись с Content. Контекст метаданных Content привязан к конкретному неизменяемому принятому пакету/снимку и не изменяет активное состояние на prepare; при изменении только метаданных переиспользовать тот же store/байты. Отдельный моддинг-снимок, обновляемый до или после commit Content, создавал бы окно рассинхронизации при отмене/stop; не вводить второй coordinator.

## Acceptance criteria

- AC1 — числовые границы и Shared/side применяются точно; отсутствующая optional не создаёт ребро; доступная совместимая цель загружается первой. Старая версия без сравнения и старый no-dependencies manifest работают.
- AC2 — malformed declarations, неоднозначный ID, обязательная отсутствующая/непригодная цель, несовместимая optional и цикл отклоняют startup до первой Lua VM и ID-публикации. Диагностика содержит ID мода, сторону/цель и причину. Client-only payload не закрывает Server dependency, и отвергнутый cooked пакет не выдаётся за принятый.
- AC3 — единый порядок Lua lifecycle и Content даёт одного победителя независимо от обхода диска. Lua code-only и base Content reload сохраняют соответствующую frozen-проекцию; при отсутствии рёбер порядок прежний.
- AC4 — `has_dependency` работает в top-level на текущей стороне, возвращает `false` для незаявленного/транзитивного/неактивного/отсутствующего и сохраняет результат при code-only reload; Lua API не раскрывает глобальный список модов.
- AC5 — валидное content-only обновление состава/совместимых метаданных упорядочивается и публикуется атомарно. Невалидный граф, изменение порядка или результата API активного Lua, ошибка пакета и отмена сохраняют старые метаданные, ID/версии и Lua-объекты. Повтор и случай restart-required с удержанием предыдущего пакета читают именно его принятую декларацию, не изменённую папку.
- AC6 — Static/Dynamic × Client/Server и Lua-only без Content подтверждены прикладными проверками. Нет изменений кадрового пути/владения; автоматизируемое поведение подтверждено Strict Red→Green→Refactor. Демка и NativeAOT запуска всей игры остаются общей приёмкой Modding 0.7, не утверждаются этим срезом.
