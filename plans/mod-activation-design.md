# Включать и отключать моды до запуска ModSet

- Status: ready
- Started: 2026-11-24
- Updated: 2026-11-24
- Revision: 2
- Complexity: medium (auto)

## Goal and scope

Дать игроку или оператору возможность не загружать установленный мод, не меняя файлы пакета. Только выбор при старте нового ModSet. UI, CLI, изменение на лету, миграция состояния, согласование между клиентом и сервером и финальная демка не входят в задачу.

## Requirements and behavior

- Пользовательский `mods.json` содержит список `disabled` из точных, регистрозависимых ID. Удаление ID включает мод при следующем запуске ModSet; отсутствие файла сохраняет прежнее поведение.
- `mods.json` рядом с `Mods/`, то есть под `IFileSystem.RootPath` (для stock PhysicalFileSystem — рабочий каталог процесса). Одна политика на корень, без групп Client/Server; разные корни могут иметь разные списки. Файл — JSON-объект с единственным обязательным полем `disabled` (массив непустых и не состоящих только из пробелов строк). Неизвестный ID не ошибка (например, мод временно удалён); повторы в массиве эквивалентны одной записи; пустой массив эквивалентен отсутствию файла. Нечитаемый или неверный явно заданный конфиг останавливает подготовку, не включая всё молча.
- Выключенный мод не регистрирует и не исполняет Lua, не предоставляет cooked-пакет или подмены и недоступен как зависимость; обязательная цель останавливает запуск, необязательная отсутствует. Override на такой мод ведёт себя как override на недоступного владельца: пропустить правило и сообщить диагностикой.
- Уже выбранный список не перечитывается при Lua code reload, base Content reload или mod Content refresh. Refresh может менять разрешённые пакеты по прежним правилам, но не применять изменения `mods.json`.

## Architecture and integration

Stock Modding.Lua владеет выбором. `ModsRegistry` сейчас собирает декларации/ID владельцев, Lua definitions и кандидатов на Content. Те же результаты питают startup resolver и `IModContentParticipant`; `LuaModContentRefresh` отдельно вызывает discovery. Поэтому фильтр нужен на единой границе discovery и должен использовать тот же неизменяемый список при refresh. Отдельный учёт обнаруженной идентичности позволяет сохранить проверку дубликатов ID и не передать выключенных владельцев в Content composition. Не добавлять второй резолвер и не менять Content Runtime только ради пользовательского файла.

Источники контрактов: [mod dependencies](../docs/modules/modding/mod-dependencies.md), [mod packaging](../docs/mod-content-overrides.md), [Content snapshot ADR](../docs/02_ADR/content-runtime-snapshots.md#mod-overrides).

## Constraints

Ветка `codex/mod-activation` от `codex/modding-0.7` (`872b052`), PR в родителя, по явному разрешению разработчика; `main` не затрагивается. Только cold-path I/O, bounded read и ordinal lookup; никаких новых проверок в Update/FixedUpdate, ECS, Lua dispatch или Content slot lookup. Не изменять каталог/VM при отказе, сохранить Client/Server/Shared boundaries. Любые распознаваемые дубликаты ID установленных модов остаются фатальными независимо от выбора.

## Decisions and alternatives

- D1 — источник: **пользовательский `mods.json` с `disabled`**. Выбран разработчиком. Параметры запуска требуют передачи на каждый запуск, а флаг в `mod_info.json` может исчезнуть при обновлении пакета. Список выключенных, а не список включённых, сохраняет установку новых модов по умолчанию.
- D2 — время применения: **при старте нового ModSet**. Переиспользовать выбор в cold refresh. Перечитывание только для content-only сделает одинаковый флаг непредсказуемым; полное переключение Lua на лету требует нового lifecycle и политики состояния.
- D3 — граница: **фильтрация на discovery до resolver, Lua и Content capture**. Раздельные фильтры в VM и Content могут разойтись и получить разные граф/порядок. Отдельно вести проверку идентичности обнаруженных модов.
- D4 — выключенный мод с синтаксически читаемым manifest и распознаваемым ID: **проверять идентичность/дубликаты, не валидировать остальную декларацию и payload**. Выбран разработчиком: отключение позволяет восстановить запуск после невалидной декларации либо payload. Полная валидация всех установленных пакетов проще, но не даёт отключить семантически сломанный мод. Синтаксически сломанный JSON (включая лишнее значение после документа) не подлежит обходу и диагностируется по существующим правилам.
- D5 — неверный пользовательский файл: **остановить подготовку с диагностикой**. Fallback на «все включены» мог бы запустить явно отключённый скрипт; диагностика указывает путь и ошибку. Список регистрозависимый, конфиг не служит средством переименования, приоритета или ограничения доступа.

## Acceptance criteria

- AC1 — без `mods.json` поведение прежнее; точный ID выключает Lua и cooked Content, удаление ID включает их при новом старте. Некорректный файл не запускает ModSet с игнорированием выбора.
- AC2 — выключенная обязательная цель останавливает startup до Lua и публикации Content; optional даёт `false`; отключённый мод не влияет собственными рёбрами на граф. Распознаваемый дубликат ID остаётся ошибкой.
- AC3 — выключенный мод не предоставляет assets или overrides; подмена, нацеленная на его ассет из другого мода, пропускается как для недоступного владельца.
- AC4 — изменение файла после старта не применяет выбор через Lua code reload, mod Content refresh или base reload; новый запуск применяет его. Покрыть Client/Server и Lua-only путь, не меняя цикл и ownership.
