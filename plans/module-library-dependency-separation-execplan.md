# Separate Module and Library Dependencies

This ExecPlan is a living document. It must be maintained according to `plans/PLANS.md`.

## Purpose / Big Picture

Make the project files express two different concepts explicitly. A `KarpikModuleDependency` will mean that one runtime module requires another runtime module and therefore participates in module selection, disabled-dependency validation, and module load ordering. A standard `ProjectReference` will mean an ordinary compile-time dependency on an engine, first-party, or third-party library. After the change, a developer can inspect any project under `Modules/` and distinguish runtime composition from library linkage without consulting the generated catalog.

## Surprises & Discoveries

- Observation: `KarpikModuleDependency` is currently expanded to a normal `ProjectReference` by `Directory.Build.targets`, so the proposed change has no runtime or hot-path impact.
  Evidence: `Directory.Build.targets` transforms `@(KarpikModuleDependency->'%(ResolvedProjectPath)')` into `ProjectReference`.
- Observation: the current catalog contains every solution project, although only projects under `Modules/` become `PluginReference` entries in `AutoGenerated.targets`.
  Evidence: `Configurator/ArtifactGenerator.cs::BuildCatalog` starts from `model.ProjectsByPath`, while `BuildTargets` starts from `graph.ActivePlugins`.
- Observation: the working tree already contains an in-progress move of the root `DragonExtensions` project into `first-parties/DragonECS.Karpik.Extensions`; these changes belong to the user and must be completed rather than reverted.
  Evidence: Git status records the old project files as deleted, the submodule as added, and several references as partially migrated.
- Observation: infrastructure projects suppressed globally injected code generators by removing `KarpikModuleDependency` IDs. A direct conversion to `ProjectReference Remove` using `$(MSBuildThisFileDirectory)` did not match because that property is scoped to the currently evaluated project file.
  Evidence: the first ECS build ran Network generators in `Karpik.Engine.Tooling` and failed on generated namespaces; `dotnet msbuild ... -getItem:ProjectReference` showed root-absolute identities defined by `Directory.Build.props`.
- Observation: a stable `KarpikRepositoryRoot` property is required so global analyzer `Include` and per-project `Remove` declarations produce identical MSBuild item identities.
  Evidence: after both declarations used `$(KarpikRepositoryRoot)`, Tooling evaluated with no Network/Stat analyzer references and the same ECS build passed with zero errors.
- Observation: physical placement below `Modules/` is not sufficient to classify a source project as a runtime module because test projects may live there without participating in selection or lifecycle.
  Evidence: `Modules/Client/Input.Tests` directly references the tested module; a RED regression test reproduced the false positive until validation used `model.Plugins` for both source and target classification.

## Decision Log

- Decision: Classify dependencies by the target project's repository path rather than adding project-kind metadata.
  Rationale: `Modules/` is already the authoritative runtime-module boundary used by Configurator, and explicit metadata would duplicate that source of truth.
  Date/Author: 2026-08-09 / user and AI assistant
- Decision: Allow module projects to reference non-module projects with standard `ProjectReference`, but reject direct references whose resolved target is another project under `Modules/`.
  Rationale: standard library references need no runtime selection semantics, while module-to-module edges must remain visible to selection and load-order validation.
  Date/Author: 2026-08-09 / user and AI assistant
- Decision: Validate Client/Server/Shared boundaries for both dependency kinds.
  Rationale: changing the MSBuild item type must not create a route around side isolation.
  Date/Author: 2026-08-09 / user and AI assistant

## Outcomes & Retrospective

The repository now has a semantic split between runtime module dependencies and ordinary compile-time library references. Generated catalog entries are limited to runtime module candidates, disabled module selection remains the sole source of `PluginReference` staging, and the DragonECS extension is consumed from its first-party submodule path. ## Context and Orientation

`Configurator/RepositoryParser.cs` reads projects listed in `KarpikEngine.slnx`. It treats projects under `Modules/` as runtime plugin candidates, records raw `ProjectReference` paths in `ProjectInfo.DirectProjectReferences`, and resolves `KarpikModuleDependency` IDs through a catalog of project filenames, aliases, and logical core-module IDs.

`Configurator/GraphValidator.cs` currently rejects every direct `ProjectReference` found in a module project. It validates side boundaries, disabled dependencies, and load-order cycles only through `ProjectInfo.Dependencies`, which currently represents `KarpikModuleDependency` items.

`Configurator/ArtifactGenerator.cs` generates `Generated/KarpikModuleCatalog.props`, `AutoGenerated.targets`, and `Generated/ModuleLoader.cs`. The catalog currently maps all solution projects, including libraries. `AutoGenerated.targets` already contains only selected module projects, so disabled modules are not staged. Library assemblies enter a staged output only as transitive output of an enabled module or another selected/root project.

`Directory.Build.props` injects analyzer dependencies using `KarpikModuleDependency`; these analyzers are not runtime modules and must become analyzer `ProjectReference` items. Module `.csproj` files currently mix real module IDs with engine, Karpik.Jobs, Veldrid, DragonECS, and DragonExtensions IDs.

## Real-Time Assessment

This work changes repository parsing, validation, MSBuild project evaluation, project files, generated build artifacts, and documentation only. It does not touch `Update`, `FixedUpdate`, ECS `Run`, render loops, serialization loops, or network pumps. It adds no runtime allocations, locks, waits, data-layout changes, or tick behavior. Client/Server/Shared separation is explicitly preserved by validating resolved direct project references with the same `IsSideAllowed` rule used for module dependencies.

## Validation and Acceptance

Acceptance requires all of the following observable conditions:

- Configurator accepts module-to-library direct project references.
- Configurator rejects module-to-module direct project references with an actionable diagnostic.
- Configurator rejects `KarpikModuleDependency` targeting a non-module project.
- Direct project references cannot cross Client/Server/Shared boundaries.
- Disabled modules and libraries referenced only by them are absent from generated `PluginReference` entries.
- The generated module catalog contains no first-party, third-party, engine infrastructure, executable, or test project IDs.
- No project file references the deleted root `DragonExtensions/DragonExtensions.csproj`.
- Every remaining `KarpikModuleDependency` in `Modules/` resolves to a project below `Modules/`.
- Targeted builds and tests pass with single-node MSBuild and node reuse disabled.

## Idempotence and Recovery

Configurator generation and code-graph refresh are safe to rerun. Project-file migration is mechanical but must preserve existing metadata and user changes. Do not reset or restore the dirty tree. If a generated-artifact comparison fails, fix the source model or project declarations and rerun Configurator rather than editing generated files manually. If a migrated reference is wrong, use the previous `KarpikModuleCatalog.props` mapping and the target project's path in `KarpikEngine.slnx` to reconstruct the correct relative `ProjectReference`.
