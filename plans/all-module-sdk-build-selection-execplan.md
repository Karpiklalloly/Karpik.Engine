# All-module SDK payload with game-owned build selection — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Keep this ExecPlan updated while work proceeds.

**Goal:** Publish every production runtime module candidate in one engine installation while allowing each game repository to select its module graph during build.

**Architecture:** Configurator remains the source of truth for module candidates, logical modules, implementations, sides, and dependencies. The packager builds all candidates and writes a versioned catalog; the SDK resolves the game's `KarpikModuleSelection` items into one canonical graph, which Static consumes as compiler references and Dynamic consumes as an engine-module manifest.

**Tech Stack:** C#/.NET 10, MSBuild SDK targets/tasks, System.Text.Json, xUnit, existing Karpik Configurator, engine payload layout v3 with a versioned catalog extension.

**Spec:** `docs/superpowers/specs/2026-09-20-all-modules-sdk-build-selection-design.md`

This ExecPlan is a living document and must be maintained according to `plans/PLANS.md`.

## Global Constraints

- The choice belongs to the game build, not to the player or runtime operator.
- Tests, tools, executables, analyzers, and ordinary libraries are not packaged as runtime module candidates.
- Configurator's plugin model is the source of truth; do not replace it with a raw `Modules/**/*.csproj` scan.
- Static and Dynamic composition must resolve the same canonical selected-module set.
- No edited code may allocate in `Update`, `FixedUpdate`, ECS `Run`, render loops, serialization loops, or network pumps.
- Preserve Client / Server / Shared boundaries and reject side leaks before compilation or startup.
- Use single-node MSBuild validation: `-m:1 -nr:false`.

## Review Focus

- An unlisted catalog module must remain absent from Static compiler references and Dynamic engine-module loading; cover in SDK selection tests and runner tests.
- A logical module with multiple implementations must reject zero-or-multiple implementations and select exactly the requested one; cover in catalog selection tests.
- A selected module's required dependency must be included even when it was not explicitly listed, while an optional dependency must not be invented; cover in dependency-closure tests.
- A Client-only module must never enter a Server graph, and a Shared project must never receive side-specific modules; cover in side-filter tests.
- Existing layout-v2/v3 installations and legacy catalog entries must fail with a clear compatibility diagnostic or follow the explicitly selected compatibility path; cover in installation validation tests.

## Surprises & Discoveries

- Observation: The packager currently reads active `PluginReference` entries from `AutoGenerated.targets`, so engine publication is tied to the engine repository's active profile.
  Evidence: `Karpik.Engine.Packager/PayloadLayout.cs`, `ReadSelectedModuleProjects`.
- Observation: Static resolution currently receives only `Side` and selects every catalog entry for that side.
  Evidence: `Karpik.Engine.Sdk/Sdk/Sdk.targets` and `Karpik.Engine.Sdk.Tasks/ResolveKarpikStaticReferencesTask.cs`.
- Observation: Dynamic loading constructs `ModuleLoader` with every catalog module and therefore needs a separate game-owned engine-module selection manifest; the existing game `modules.list` describes staged game assemblies.
  Evidence: `Karpik.Engine.Core.Runner/Program.cs`, `Karpik.Engine.Core.Runner/RuntimeModuleComposition.cs`, and `Karpik.Engine.Core/ModuleManagement/ExternalModuleComposition.cs`.

## Decision Log

- Decision: Keep Configurator as the module-discovery source of truth and expose a package-catalog output for the packager.
  Rationale: Avoid a second filename/path heuristic that can package tests, libraries, or stale implementations.
  Date/Author: 2026-09-21 / Codex
- Decision: Make game selection explicit through evaluated `KarpikModuleSelection` items; unlisted logical modules are disabled for external game builds.
  Rationale: Adding all catalog entries must not silently change a game's composition.
  Date/Author: 2026-09-21 / Codex
- Decision: Use one normalized selection resolver for Static references and Dynamic manifests.
  Rationale: Separate selection logic would drift in dependency closure, side filtering, or implementation conflict handling.
  Date/Author: 2026-09-21 / Codex
- Decision: Extend the module catalog with logical id, kind, implementation id, dependency ids, and a catalog format version; reject older catalogs when selection metadata is required.
  Rationale: The installed engine has no checkout `.csproj` files, so build-time selection must be resolvable from the payload alone.
  Date/Author: 2026-09-21 / Codex

## Outcomes & Retrospective

The published SDK now carries the complete production module inventory. Games select logical modules
and implementations in `Directory.Build.props`; Static references and Dynamic engine manifests use
the same dependency-closed result. Legacy catalogs are still accepted for validation-only paths but
are rejected when a game requests build-time selection, preventing silent fallback to the old
"everything on this side" behavior.

The external CLI test reaches the new selection path and passes against a temporary layout-v4-
compatible copy of the retained fixture; the retained installation itself remains untouched and
legacy catalogs still fail with the intended compatibility diagnostic.

## Context and Orientation

`Configurator/RepositoryParser.cs` already filters solution projects below
`Modules/`, excludes test and executable projects, classifies plugins as
standalone/core/implementation, and records dependency metadata. `GraphValidator`
uses the active profile to produce `GraphResult.ActivePlugins`; that active list
is correct for game composition but too narrow for a complete engine payload.

`Karpik.Engine.Packager/PayloadLayout.cs` builds the engine/editor/runner/tool
artifacts and currently copies only projects returned by
`ReadSelectedModuleProjects`. It writes `modules/modules.catalog` with only a
side and concrete module id.

`Karpik.Engine.Tooling/EngineModuleCatalog.cs` validates that catalog and exposes
`ForSide`. `Karpik.Engine.Sdk.Tasks/ResolveKarpikStaticReferencesTask.cs` uses
that API during MSBuild evaluation. `Karpik.Engine.Sdk/Sdk/Sdk.targets` adds the
returned references to Runtime and Static Tool projects.

Static hosts receive generated composition from the compiler-visible module
references. Dynamic hosts use `RuntimeModuleComposition` and `ModuleLoader`; the
runner must receive only the game-selected engine module descriptors while its
existing game-assembly manifest remains intact.

The accepted module-graph ADR says runtime module candidates are explicit,
dependencies use `KarpikModuleDependency`, and tests/infrastructure/libraries do
not participate in module selection. The new behavior changes packaging and
external-game selection, not lifecycle ordering.

## Real-Time Assessment

This change is limited to engine publication, MSBuild evaluation, bundle
materialization, and runtime startup. It does not add work to `Update`,
`FixedUpdate`, ECS systems, render loops, serialization loops, or network pumps.

Catalog parsing and selection allocate short-lived metadata collections during
build/startup. That is acceptable outside the real-time loop. Runtime module
access remains through already loaded assemblies; no per-frame lookup, lock, or
reflection path is introduced. Module DLLs remain isolated in their existing
directories and shared dependencies remain deduplicated in `shared/`.

The resolver must preserve side boundaries before references or descriptors are
returned. No Client project may reference Server modules, and no Server project
may reference Client modules. Shared projects receive only Shared candidates.

No fixed-dt or ECS data-layout changes are involved. Concurrency is unchanged;
the only new runtime operation is bounded startup manifest validation.

## Plan of Work

### Milestone 1 — Catalog contract and canonical selection resolver

Modify `Karpik.Engine.Tooling/EngineModuleCatalog.cs` and add the selection
types beside it. Extend each catalog record with concrete module id,
logical module id, `EngineModuleKind`, side, optional implementation id, and
canonical dependency records. Add a format/version marker and keep sorting and
safe-id validation deterministic. Keep the legacy two-field parser for
validation-only paths; when the selection resolver receives such a catalog it
must return a typed "selection metadata missing" failure and never treat the
old catalog as a complete selectable catalog.

Add `EngineModuleSelectionResolver.Resolve(...)` in `Karpik.Engine.Tooling`.
It must accept the catalog, evaluated logical selections, and requested side;
return the selected concrete entries in canonical order; add required
dependencies recursively; omit disabled and optional dependencies; reject
unknown logical ids, invalid implementations, duplicate CLR identities,
conflicting implementations, missing required dependencies, and side leaks.

Extend `Karpik.Engine.Tooling.Tests/ManifestAndValidationTests.cs` or add a
focused `EngineModuleSelectionTests.cs` for canonical serialization, logical
selection, dependency closure, conflicts, missing dependencies, and side
filtering. Run the tooling test project before moving on.

### Milestone 2 — Configurator package-catalog output

Modify `Configurator/ArtifactGenerator.cs` and `Configurator/Program.cs` to
expose a non-interactive package-catalog command that serializes every
`RepositoryModel.Plugins` runtime candidate, not only `GraphResult.ActivePlugins`.
Include repository-relative project path, concrete plugin id, logical module id,
kind, side, implementation id, and normalized dependency ids. Keep output
canonical and deterministic so the packager can reject stale or malformed
catalog input.

Add Configurator tests covering a disabled implementation that still appears in
the package catalog, test/executable projects that do not appear, and stable
ordering. Keep `--validate` and `--generate` behavior unchanged for the active
game graph.

Run:

    dotnet test Configurator.Tests/Configurator.Tests.csproj -m:1 -nr:false

Expected result: existing graph validation passes and the new catalog snapshot
contains all production plugin candidates regardless of active selection.

### Milestone 3 — Packager builds and publishes the complete module inventory

Modify `Karpik.Engine.Packager/PayloadLayout.cs` so repository mode obtains the
complete package catalog from Configurator, builds every catalog project once,
copies every primary module output into `modules/<ModuleId>`, and writes the
extended validated `modules.catalog`. Do not read active `AutoGenerated.targets`
for package membership. Keep `StageModuleNativeAssetsForRunners`, shared-store
deduplication, PDB filtering, and collision checks intact.

Set `EngineInstallationManifest.CurrentLayoutVersion` to 4 for the extended
catalog contract. Update `EngineInstallationValidator.cs` to validate layout
4 metadata while preserving explicit coverage for legacy layout-v2/v3 fixtures;
the new SDK resolver must reject a legacy catalog when game-owned selection is
requested instead of silently selecting every entry.

Add repository-mode packager tests in
`Karpik.Engine.Packager.Tests/EnginePayloadBuilderTests.cs` proving that an
unselected implementation is present, test projects are absent, the catalog
matches the module directories exactly, and native assets remain side-correct.

Run:

    dotnet test Karpik.Engine.Packager.Tests/Karpik.Engine.Packager.Tests.csproj -m:1 -nr:false
    dotnet test Karpik.Engine.Tooling.Tests/Karpik.Engine.Tooling.Tests.csproj -m:1 -nr:false

Expected result: a repository payload contains the complete production module
inventory and remains valid under installation validation.

### Milestone 4 — Static SDK consumes game-owned selection

Modify `Karpik.Engine.Sdk/Sdk/Sdk.props` or `Sdk.targets` to make evaluated
`KarpikModuleSelection` items available to the resolver. The consumer-facing
shape is:

    <ItemGroup>
      <KarpikModuleSelection Include="ECS" Enabled="true" />
      <KarpikModuleSelection Include="Graphics" Enabled="true" Implementation="OpenGL" />
    </ItemGroup>

Modify `Karpik.Engine.Sdk.Tasks/ResolveKarpikStaticReferencesTask.cs` to call the
shared resolver with the current side and selection items. Keep the existing
`References` and `PayloadAssemblies` outputs, but return only the normalized
selected graph. An external game with no `KarpikModuleSelection` item group
must fail with a stable diagnostic; once the group exists, unlisted logical
modules are disabled. The resolver must still enforce required dependencies and
the ECS baseline.

Add task tests proving an unselected catalog entry is absent from both outputs,
an implementation choice selects only its concrete assembly, and an opposite
side module cannot enter the result. Preserve the existing side-safe shared DLL
filter regression.

Run:

    dotnet test Karpik.Engine.Sdk.Tasks.Tests/Karpik.Engine.Sdk.Tasks.Tests.csproj -m:1 -nr:false

Expected result: Static game and Static Tool projects compile only against the
selected module graph.

### Milestone 5 — Dynamic bundle and runner consume the same selection

Modify `Karpik.Engine.Sdk/Sdk/Sdk.targets` and
`Karpik.Engine.Sdk.Tasks/BuildKarpikRuntimeBundleTask*` to materialize a
canonical engine-module selection manifest alongside the existing game-module
manifest. The manifest must contain concrete selected module ids, be bounded,
sorted, UTF-8/LF canonical, and be covered by the existing completion/hash
validation.

Modify `Karpik.Engine.Core/ProcessManagement/RuntimeLaunchOptions.cs`,
`Karpik.Engine.Core.Runner/RuntimeModuleComposition.cs`,
`Karpik.Engine.Core.Runner/Program.cs`, and the corresponding tests so the
universal runner reads the game-owned engine-module manifest and constructs
`ModuleLoader.EngineModuleDescriptor[]` only for those entries. The runner must
reject missing, duplicate, unknown, side-incompatible, or catalog-mismatched
module ids before loading assemblies.

Add Dynamic integration coverage for two manifests produced from one engine
installation: each loads its own module set and neither loads an unselected
module. Keep the existing game-owned `modules.list` contract separate from the
new engine-module selection manifest.

Run:

    dotnet test Karpik.Engine.Core.Runner.Tests/Karpik.Engine.Core.Runner.Tests.csproj -m:1 -nr:false
    dotnet test Karpik.Engine.Sdk.IntegrationTests/Karpik.Engine.Sdk.IntegrationTests.csproj -m:1 -nr:false

Expected result: two manifests from one installation load different selected
engine-module sets and reject malformed or side-incompatible manifests.

### Milestone 6 — Template, documentation, and end-to-end acceptance

Update `templates/Karpik.Game` with an explicit example/default
`KarpikModuleSelection` profile and document how developers change it. Update
`Karpik.Engine.Sdk/README.md`, `templates/Karpik.Game/README.md`, and
`docs/02_ADR/module-graph.md` to distinguish the complete installed inventory
from the game-selected build graph.

Add external-game integration tests that build two game projects against the
same installed engine payload with different selections in both Static and
Dynamic modes. Assert that the resulting compile/runtime module sets differ,
that dependencies are included, and that the unselected module's installer or
service cannot be resolved.

Run the final targeted suite and then the full solution test/build commands.

## Validation and Acceptance

Acceptance is observable when one published engine installation contains every
production module candidate, while two game builds using different
`KarpikModuleSelection` profiles produce different Static compiler graphs and
different Dynamic engine-module manifests. Both builds must start successfully;
unselected module installers must not be registered; selected required
dependencies must be present; test/tool projects must not appear in the
payload; and all existing side-safety, catalog, AOT, and hot-reload tests must
remain green.

## Idempotence and Recovery

Catalog generation, builds, tests, and payload publication are safe to rerun
after cleaning only their owned temporary/artifact directories. Do not delete
the user's engine installation or NuGet cache as part of tests. If a new
catalog/layout version makes an installation invalid, leave the old validated
installation intact and publish the new version into its normal atomic staging
path; restore by selecting the previous validated installation. Never reset or
discard unrelated working-tree changes.
