## Requirements and behavior

Preserve typed CLR/dynamic component access, access declarations and Simulation ownership. D1-D13 below are user-selected behavior. Deferred changes are visible only after a successful callback and full validation, before the next scheduled system. No new direct entity destruction, persistent creation receipts, deferred set/upsert, individual FixedUpdate adapters, save/network/reload, VM cancellation/timeouts or sandbox changes are included.

The public surface is `ctx.commands:create()`, `ctx.commands:add(pool, target [, snapshot])`, and `ctx.commands:del(pool, target)`. `pool` is the existing query component handle. `target` is either a pending token or an existing numeric entity ID. These names make the separate deferred API explicit; `ctx:create` in the initial topic was the entity-creation capability, not an existing API to preserve. Add/del return no live ECS view. Omitted payload performs default initialization; snapshot input supplies only writable leaves. Readonly native leaves keep default values, not copied snapshot values. All supported writable scalar/nested/fixed/exact/native-width fields and opt-in pointers remain supported; command input does not bypass readonly or pointer policy.

Every token must receive a component before batch completion, and no deferred del may leave its target without a logical component at any point. A game-defined marker counts as a component; DynamicComponentAnchor is technical and does not count. Preflight uses all native components and all dynamic components, including ones absent from the system's declared queries, to determine whether a component is the last one.

## Architecture and integration

Verified in current checkout: LuaEcsContext pool add/del call PreparedComponentHandle directly; Add returns a live reusable view and Del mutates its pool immediately. Query membership is materialized into an ID snapshot, with current data read during iteration (plans/lua-ecs-bindings-spec.md). The older script-modding-design.md requires a preallocated structural command buffer but explicitly leaves application points and command conflicts unresolved. This is a contract reconciliation, not a completed buffer implementation.

Core mechanics belong in Shared/Modding.Core, MoonSharp adaptation in Shared/Modding.Lua; services use constructor injection and Simulation lifetime. Preserve sequential Lua execution and infer writes from the specific mutable query handles; verify the chosen post-callback boundary through the real scheduler.

Command storage is owned by Simulation and reused across sequential callbacks; handles retain per-system ownership. Do not allocate a maximum-size queue for every Lua system when their callbacks cannot overlap. Prepared handle metadata is resolved at startup; command records and payload/validation storage are dense bounded arrays. The host configures callback limits through Simulation-scoped constructor-injected options; provide bounded defaults of 1024 command operations (including create), 256 pending entities and 256 KiB payload, with checked startup validation and explicit overrides. Zero budget disables command submission while preserving existing APIs. Token generation/invocation identity must not wrap into a valid retained token; reject exhaustion. Immutable Lua token wrappers may allocate under the separately specified experimental VM budget; never rebind retained token objects to a later invocation.

Existing numeric targets capture world/generation at enqueue and are revalidated before playback. A raw number already stale before enqueue retains the pre-existing int-ID limitation; this stage does not retrofit persistent generation-safe Lua entity references. Snapshot values are copied at enqueue, including policy tokens; validate pointer policy again during preflight. Schemas remain frozen for Simulation, and no other thread may revoke pointer policy or mutate world concurrently with preflight/playback.

Per-callback execution is: enter owner scope and reset queue; run callback; if successful and queue valid, preflight then synchronously apply; always invalidate tokens/reset queue and exit scope. Predictable command errors use existing ScriptSystemErrorPolicy: StopSimulation propagates to host, LogAndContinue logs contextual information then proceeds to following systems with the deferred batch discarded. Unexpected errors during playback stop Simulation regardless of that setting. OperationCanceledException propagates and discards an unapplied queue; no new asynchronous cancellation facility is added, and successful bounded playback is not interrupted halfway by a new polling mechanism. Disposal follows existing Simulation ownership and cannot race an active callback.

No script is invoked during preflight/playback. Commands are logically FIFO. A create declares a pending entity; physical allocation may be delayed to that token's first add, which immediately attaches its first component. There is no externally usable real entity ID before playback. Backend NewEntity events therefore follow physical materialization order, which can differ from pending-token declaration order; no promise of token-order numeric IDs or new transactional event batching is made. Existing native event hooks remain synchronous and must obey the backend's non-reentrant mutation contract; this feature does not guarantee safety or no-GC for arbitrary host listener code. Unexpected reentrant mutation is an infrastructure failure, not a recoverable script validation error. Detect relevant invariant changes and stop rather than silently apply against stale validation.

No-growth playback checks world entity slots, native pool Capacity-1, dynamic pool dense capacity, anchor capacity and FIFO peak occupancy, rather than final counts alone. In normal backend lifecycle, free entity slots equal `world.Capacity - 1 - world.Count - world.DelEntBufferCount`: the null slot and unreleased deletions consume dispenser entries. Preflight must not call world.Entities/ToSpan, which can release deletions and mutate the world. Native initial pool capacity is set by EcsWorldConfig; dynamic pools inherit its pool capacity. Expose prepared capacity metadata in the binding layer as needed; use already reserved capacities and reject insufficient capacity without growth. A new runtime reserve API or a third-party source change is not part of this slice. Host startup world configuration may provide larger native capacities. Existing immediate APIs may still grow according to their earlier contract; no zero-allocation claim covers those calls or arbitrary whole Lua callbacks.

Performance acceptance proposed for the implementation-plan approval: common successful warmed enqueue + preflight + playback must allocate 0 B, including tokens, scalar/nested/fixed payloads and native/dynamic operations. Startup, fresh snapshot construction, error diagnostics and teardown are measured separately. New canonical Lua command workload ceiling is `4096 + 1600*C + 1600*V + 544*O` B/callback, where C includes create/add/del, V is the total scalar leaves explicitly prepared/copied into command snapshot payloads in that callback, and O is exact arithmetic operations. Use prepared snapshots, deterministic workloads and C derived from N=0/1/16/256/4096 entities with test-specific limits large enough for each case. This is an upper bound for named test workloads, not arbitrary scripts; record raw bytes, time, Gen0 and memory separately. Existing typed/f32/composite ceilings remain unchanged. Failure of this proposed new gate requires analysis and a scoped budget decision; do not raise it silently.

## Decisions and alternatives

- D1 — accepted by user (answer `1`): preserve immediate add/del and introduce a separate explicit command API. Separate API retains existing scripts and live-view behavior, at the cost of two explicit mutation models. Rejected alternative: full migration gives one deferred model but breaks current add-returned-view and immediate has/get behavior.
- D2 — accepted by user (answer `1`): apply commands after their owning callback and before the next scheduled system. Commands do not mutate the world during that callback. Per-callback application supports Lua A -> native B -> Lua C dependencies with same-phase visibility and shorter pending-handle lifetime. Rejected alternative: phase-end application batches more work but delays visibility and requires a shared flush boundary. No explicit in-callback flush is selected. Error-path handling is resolved by D3/D9/D13.
- D3 — accepted by user (answer `1`): discard the callback's queued commands if it fails; retain existing immediate writes and immediate add/del. Rejected alternative: applying the queued prefix matches immediate partial-write behavior more closely but can expose unfinished deferred entity initialization. This does not promise rollback or atomicity of command playback, whose failure behavior still needs a decision.
- D4 — accepted by user (answer `1`): creation returns a callback-local pending token usable only by the deferred API. The entity is absent from the world until playback; immediate pools reject this token. The token expires after its callback and requires owner/invocation validation. Rejected alternative: reserve real entity identity before playback, which requires backend reservation/rollback and protection against visibility and ID reuse. Post-playback access is resolved by D5 (queries only).
- D5 — accepted by user (answer `1`): recover created entities through declared component queries in later callbacks. No persistent creation receipt in this slice. Queries reuse the current API without result storage/lifetime overhead; exact-instance lookup requires a suitable component discriminator such as a game-defined ID. Rejected alternative: a separate persistent creation receipt supports direct addressing but requires retained result storage, release/capacity/failure semantics and an entity lifetime contract. The pending token remains callback-local per D4.
- D6 — accepted by user (answer `1`): include deferred create and component add/del for both pending tokens and existing entities. Direct entity destruction remains excluded; preserve the prior marker-based deletion direction. Rejected alternative: creation-only reduces integration and conflict cases but leaves existing-entity deferred edits for a later stage.
- D7 — accepted by user (answer `1`): add optionally accepts a compatible ComponentSnapshot and captures its writable values into queue-owned preallocated storage at enqueue time. Later snapshot edits do not affect queued commands; callers may reuse a prepared snapshot buffer. Omitted payload means normal default component initialization. Existing readonly/host-pointer rules remain enforced; whole-component raw memcpy and readonly write bypass are not implied. Rejected alternative: mutable queue staging view avoids an intermediate copy but adds view lifetime/invalidation hazards. Fresh snapshot construction still allocates and is excluded from the warmed no-GC path.
- D8 — accepted by user (answer `1`): execute commands in enqueue order with strict add/del preconditions. Reject add on an already present component and del on an absent one. No command coalescing that changes semantics. Preconditions refer to playback state including preceding queued commands and immediate callback mutations, not merely enqueue-time membership. Rejected alternative: idempotent ensure-present/ensure-absent hides conflicts and needs payload precedence rules. Failure handling is D9; no full infrastructure rollback is promised. Strict ordering does not guarantee that del->add succeeds when deletion removes the entity's last component; backend entity lifecycle must be accounted for.
- D9 — accepted by user (answer `1`): preflight the entire queue against post-callback world state and simulated FIFO membership/liveness before applying any deferred mutation. Predictable script errors discard the entire deferred queue; immediate callback writes remain. Costs: additional validation pass and preallocated validation state. Rejected alternative: direct application until the first invalid command retains partially initialized batches. No full rollback promise: unexpected infrastructure/playback failures stop the Simulation and must not be swallowed by LogAndContinue. Preflight must cover target identity, permissions, component membership/liveness transitions, payload/pointer validity and required capacity where these can be checked without world mutation. Mechanics were validated by common/integrated tests during execution; see evidence.
- D10 — accepted by user (answer `1`): host configures fixed per-system callback limits for command count, pending creations, payload bytes and validation scratch; reserve before callbacks and invalidate the entire batch on overflow, even if Lua catches the enqueue error. Rejected alternative: per-system Lua budget declarations add public declaration/startup-validation surface. Growing arrays on demand introduces allocations/copy spikes and is unsuitable for the new no-GC path. Splitting overflow across callbacks changes D2 visibility and D9 batch semantics. ECS world/pool capacity is a separate budget, enforced by D14 and the no-growth contract; queue reservation alone does not establish no-GC playback.
- D11 — accepted by user (answer `1`): deferred component operations require a specific existing mutable query pool handle owned by this callback. Readonly handles remain readonly even if another query has mutable access. Existing mutable handles infer scheduler Write, including DynamicComponentAnchor for dynamic edits. Query membership itself does not constrain target identity, consistent with current pool operations. Rejected alternative: separate command-write declarations decouple spawning from queries but add declaration/parser/validation and scheduler inference contracts.
- D12 — accepted by user (answer `1`): reject a deferred del that removes an entity's final component (counting all native and dynamic components, excluding the technical DynamicComponentAnchor from logical count), and require each create to receive a component. Scripts replacing the last component must add its replacement before deleting the old one. Immediate add/del behavior remains unchanged under D1. Rejected alternative: lifetime guards permit temporarily empty entities but introduce technical structural mutations, listener/access accounting and cleanup semantics. Newly created entities necessarily start empty internally, so playback must avoid accumulating unprotected empty creations; materialization at the first add is a candidate private technique, subject to FIFO/observer consistency validation.
- D13 — accepted by user (answer `1`): every rejected deferred API operation invalidates the whole callback batch even if caught by Lua pcall. This applies to errors of the deferred API, not caught errors in unrelated Lua code or existing immediate APIs. Rejected alternative: recoverable rejected calls support fallback but may publish unfinished initialization and make overflow a special case.
- D14 — engineering derivation, approved with plan r1: capacity exhaustion is a predictable validation failure, with no queue/world/pool growth during the new path. Dynamic growth would violate the no-GC and predictable-latency constraints; defer-to-next-callback would violate D2/D9. Reuse Simulation storage rather than per-system maximum arenas to limit memory. Unmanaged arenas have no demonstrated advantage over preallocated managed arrays for this bounded linear workload and add lifetime risk; do not use them without evidence.
- D15 — integration contract, approved with plan r1: preserve current error policy for predictable failures and propagate cancellation; unexpected playback errors always stop. Capture generations internally without claiming to fix already-stale raw IDs. Lazy physical materialization at first add prevents a queue of empty new entities while keeping logical FIFO and all visible results at the D2 boundary. Immediate physical creation would require an additional lifetime guard or stricter create/add syntax; lazy materialization avoids those extra contracts while making event/ID order explicit above.

## Acceptance criteria

- AC1: deferred edits remain invisible during their callback and are applied in logical FIFO after validation, before the next scheduled system; demonstrate Lua A -> native B -> Lua C.
- AC2: reject foreign/expired/forged tokens, wrong Simulation, readonly/foreign pool handles, incompatible snapshots and targets whose captured generation changed. Preserve the documented limitation of already-stale raw numeric IDs. Enforce all host pointer rules.
- AC3: successful warmed common enqueue/preflight/playback allocates 0 B with no world/pool growth, using reserved host-configured limits and peak-capacity validation. Measure experimental canonical Lua workloads against the stated new gate without increasing previous gates; report timings and memory, without claiming production latency or arbitrary-listener zero-GC.
- AC4: preserve immediate add/del and their live-view behavior; expose deferred operations separately.
- AC5: callback/API/overflow/preflight errors discard all deferred changes, including caught command API errors; preserve immediate changes. Test both existing error policies, fatal playback failures, cancellation propagation and clean reuse on the next callback.
- AC6: create requires component initialization, del-last is rejected using complete logical membership, replacing via add-new then del-old works, dynamic anchor transitions remain correct. No implicit direct-destroy API or persistent receipts.
- AC7: snapshot payload capture is independent of later changes; all supported writable kinds/nested/fixed paths initialize correctly, readonly leaves retain default, default add is supported. Revoked pointer tokens fail preflight without partial deferred changes.
- AC8: Static/Dynamic composition and Deterministic/Parallel scheduler integration preserve dependencies and Simulation lifecycle. Fresh Runner/Generator suites and independent read-only review close all actionable findings; publish only the isolated task diff or report the concrete publication blocker.
