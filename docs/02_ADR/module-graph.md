# Deterministic Module Graph

> Status: accepted
> Date: 2026-05-31
> Owners: developer and Codex
> Related ExecPlan: [[../../plans/module-graph-execplan]]

## Context

Module projects previously declared standard `ProjectReference` items while Configurator independently scanned project filenames. The two sources could drift, disabled dependencies were not rejected, generated artifacts could become stale, and side leaks were diagnosed only partially.

This work runs during MSBuild evaluation, Configurator execution, startup, and shutdown. It does not add frame-loop, fixed-tick, ECS-run, render-loop, or network-pump work.

## Decision

Runtime module projects under `Modules` declare runtime module dependencies with shorthand `KarpikModuleDependency` ids and ordinary compile-time library dependencies with standard `ProjectReference` items. A `KarpikModuleDependency` target must itself be a runtime module candidate; logical module ids such as `Physics2D` resolve to their core plugin and implementation ids such as `Physics2D.Aether2D` resolve to a concrete plugin. Engine infrastructure, analyzers, first-party libraries, third-party libraries, tests, and executables are referenced directly and do not participate in module selection or lifecycle ordering.

Configurator reads raw project XML, derives plugin identity and side from repository conventions, validates the structured profile in `Directory.Build.props`, rejects unknown and ambiguous module ids, rejects module-to-module `ProjectReference` items, and rejects `KarpikModuleDependency` items that target libraries. It generates deterministic `AutoGenerated.targets`, `Generated/KarpikModuleCatalog.props`, and `Generated/ModuleLoader.cs` artifacts. The generated catalog contains runtime modules and module aliases only. `Directory.Build.targets` imports the catalog and expands module dependency ids into evaluated `ProjectReference` items so Rider and the compiler resolve referenced module types after project reload; ordinary library references require no generated mapping.

Runtime installer lifecycle ordering remains priority-first. Equal priorities use assembly load rank, installer full type name, then registration rank. Installer teardown runs in reverse init order.

## Alternatives Considered

- Keep separate `ProjectReference` and Configurator metadata declarations. Rejected because duplicated dependency state drifts.
- Generate references only after running Configurator. Rejected because IDE type resolution must not depend on a generator run.
- Use compile-DAG order for installer lifecycle. Rejected because existing installer priorities intentionally differ from compile dependencies.

## Consequences

- New modules must be added explicitly to the structured profile.
- Adding or moving a project requires regenerating the tracked catalog.
- Invalid naming, dependency-kind mismatches, side leaks, missing dependencies, disabled required module dependencies, cycles, and stale artifacts fail before runtime.
- Configurator allocates model objects and loader startup creates descriptors; hot paths remain unchanged.
- Rider must reload projects after dependency declaration edits so evaluated `ProjectReference` items refresh.
