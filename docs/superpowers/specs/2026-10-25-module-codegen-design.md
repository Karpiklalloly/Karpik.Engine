# Генераторы, принадлежащие модулям

Дата: 2026-10-25. Статус: контракт согласован в чате; реализация не начата.

## Назначение

Добавление Roslyn-генератора к модулю не должно требовать внесения его имени в общий список генераторов движка. Генератор должен запускаться в каждой компиляции, прямо или транзитивно зависящей от модуля.

## Согласованный контракт

- Для `Foo.Core.csproj` проект генератора называется `Foo.Core.Codegen.csproj`. Генератор необязателен.
- Связь определяется точным именем проекта, а не классом `IModule` или runtime-регистрацией.
- При цепочке `Game → Gameplay → Foo.Core` генератор работает в `Gameplay` и `Game`.
- Ромб зависимостей не приводит к повторному подключению генератора в одну компиляцию.
- Распространение учитывает выбранные модули, optional-зависимости и Client/Server/Shared.
- Внешняя игра через установленный SDK получает ту же связь модуля с генератором.
- Генератор обрабатывает текущую компиляцию. Генерация по типам зависимых сборок требует явного чтения их символов внутри самого генератора.
- Генератор является инструментом сборки. Он не становится runtime-модулем, сервисом DI или зависимостью runtime bundle.
- Существующие генераторы также должны быть перенесены к соответствующим владельцам и подключаться через новый механизм; обновить их имена, пути и все потребляющие ссылки.

## Подходы

Выбран convention-based подход: обнаруживать `<имя проекта модуля>.Codegen.csproj`, сохранять связь в build metadata и подключать стандартным механизмом Roslyn Analyzer. Его предложил разработчик; транзитивное распространение подтверждено отдельно.

Явная регистрация отдельным MSBuild item позволяет произвольные имена, но добавляет дублируемую настройку. Центральный список уже существует и требует правок вне модуля. Runtime-регистрация не подходит для запуска compile-time Roslyn-генераторов.

## Технические решения плана

Это решения реализации, а не дополнительные требования разработчика: обнаружение ограничить известными проектами решения; неоднозначные совпадения отклонять с путями кандидатов; не подключать генератор автоматически к его собственному проекту или к проекту-владельцу. Для владельца сохраняется возможность обычной явной analyzer-ссылки, если это не создает цикл сборки.

Использовать существующие Configurator, каталог модулей и SDK targets. Не создавать второй resolver графа модулей. В SDK публиковать DLL генератора и необходимые ему зависимости отдельно от runtime assemblies, с путями относительно engine payload.

## Миграция существующих генераторов

Перенос входит в эту задачу по указанию разработчика от 2026-10-25. Физически размещать отдельный проект генератора рядом с проектом-владельцем, сохраняя изоляцию compile-time и runtime кода.

- `Network.Codegen` → владелец `Network.Shared.Core`, имя `Network.Shared.Core.Codegen`.
- `StatAndAbilities.Codegen` → владелец `StatAndAbilities`, имя `StatAndAbilities.Codegen` сохраняется.
- `Karpik.Content.Codegen` → владелец `Karpik.Content.Runtime`, имя `Karpik.Content.Runtime.Codegen`: генератор читает `Karpik.Content.Runtime.ContentTypeAttribute`.
- `Karpik.Engine.Core.Codegen` → владелец `Karpik.Engine.Core`, имя сохраняется; убрать лишний промежуточный каталог `Karpik.Engine.Core.Generator` при переносе.

Это исходная карта для проверки при реализации. Core и Content.Runtime находятся в `src`, а не среди выбираемых runtime-модулей `Modules`: механизм должен поддержать их принадлежность к проекту-владельцу, не превращая их искусственно в выбираемые модули. Проверить фактических потребителей каждого генератора до удаления старого подключения. `StaticAnalyzer` является анализатором правил, а не генератором; его назначение и действующее подключение сохраняются.

Миграция включает `.slnx`, ProjectReference, тестовые fixtures, SDK packaging/payload, скрипты, документацию и удаление прежних центральных подключений перенесенных генераторов. Сохранить публичные контракты и генерируемый код; изменение namespace или поведения генерации не является целью переноса.

## Границы и совместимость

Изменения ограничены build-time tooling, документацией и проверками. Нет новых runtime-вызовов, аллокаций игрового цикла, блокировок или изменений fixed dt. Формат SDK metadata должен иметь явную проверку версии и тест совместимости: старый payload без регистраций продолжает работать без модульных генераторов; неизвестная новая версия дает понятную ошибку. Генератор не может зависеть от потребителя, компиляция которого требует этот генератор: это цикл сборки.

## Приемка

Компиляционный тест должен использовать сгенерированный тип в прямом и транзитивном потребителе. Проверить ромб, отсутствие генератора, выключенный и отсутствующий optional-модуль, границы сторон, неоднозначное имя, цикл, повторную сборку и внешний проект через собранный SDK. DLL генератора и его служебные зависимости отсутствуют в runtime bundle.

Миграция завершена, когда существующие генераторы расположены у своих владельцев, старые пути и дублирующие подключения удалены, а их поведенческие тесты и проверки SDK проходят. Проверить сохранение генерации внутри самого владельца, если она была необходима до переноса: при необходимости оставить явную build-only ссылку без цикла.
