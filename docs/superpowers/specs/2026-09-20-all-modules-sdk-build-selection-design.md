# All-module SDK payload with game-owned build selection

## Goal

Publish one engine installation containing every production runtime module
candidate from `Modules`, while letting each game repository select its module
set during build. Static and Dynamic composition must use the same resolved
selection and must never activate unselected modules.

The choice belongs to the game build, not to the player or runtime operator.

## Current failure

The packager currently reads active `PluginReference` entries from
`AutoGenerated.targets`, builds only that set, and writes those modules into
the engine payload. This makes the engine installation determine what a game
can use.

Conversely, the installed SDK's static resolver currently receives only the
runtime side and selects every catalog entry for that side. Simply adding all
modules to the payload would therefore compile every module into every Static
game and would not provide game-level selection.

## Decisions

- The published payload contains all production runtime module candidates and
  implementation variants known to Configurator. Tests, tools, executables,
  analyzers, and ordinary libraries are excluded. Module discovery must reuse
  Configurator's plugin model; a raw `Modules/**/*.csproj` scan is not the
  source of truth.
- The payload keeps one validated catalog, extended as needed with the logical
  module id, concrete implementation id, side, and dependency metadata needed
  to resolve a game selection without the engine checkout.
- The game repository declares its selection with the existing
  `KarpikModuleSelection` semantics: enabled/disabled logical modules and an
  optional implementation. The selected set is normalized deterministically,
  expanded through module dependencies, and checked for missing dependencies,
  side leaks, duplicate CLR identities, and conflicting implementations.
- Static MSBuild reference resolution consumes the normalized game selection,
  not the complete catalog. Only selected module primary assemblies and their
  required payload assemblies become compiler references, so source generation
  and Static composition see exactly the selected graph.
- Dynamic builds use the same normalized selection to create the runtime
  module manifest. The universal runner loads only that manifest's modules;
  catalog presence alone never causes activation.
- Shared dependency deduplication and native asset staging remain unchanged in
  principle. Extra modules increase installation size and publish time, but do
  not add work to frame, ECS, render, or network hot paths.

## Data flow

1. Configurator classifies all repository plugins and emits the complete
   package catalog during engine publication.
2. The game build supplies its `KarpikModuleSelection` items to the SDK.
3. The SDK resolves aliases, implementations, dependencies, and runtime sides
   into one canonical selected-module set.
4. Static builds consume that set as MSBuild references; Dynamic builds consume
   it as the bundle manifest.
5. Startup validates that the produced static graph or dynamic manifest matches
   the selected set before loading game code.

## Compatibility and migration

Existing game profiles that omit an explicit selection must not silently gain
all modules. During migration, the SDK should either preserve the current
default selection or fail with a clear diagnostic requiring a selection. A
compatibility default may be retained temporarily, but it must be explicit
and documented.

## Validation

- Packager integration test proves the payload contains all production module
  candidates, including unselected implementations, and excludes tests/tools.
- Selection tests prove logical-module resolution, implementation conflicts,
  dependency closure, side filtering, and deterministic ordering.
- Static SDK task test proves an unselected catalog entry is absent from
  `References` and `PayloadAssemblies`.
- Dynamic bundle test proves `modules.list` contains only the normalized
  selection and the runner rejects a manifest/catalog mismatch.
- External game integration tests build two games with different selections
  from the same engine installation and prove their Static and Dynamic module
  sets differ accordingly.
- Existing side-safety, catalog validation, composition, and AOT tests remain
  green.

## Non-goals

- Runtime/player-controlled module switching.
- Separate engine installation or SDK package per game.
- Loading arbitrary DLLs that are not present in the validated package
  catalog.
- Changing module lifecycle ordering or adding runtime hot-path discovery.
