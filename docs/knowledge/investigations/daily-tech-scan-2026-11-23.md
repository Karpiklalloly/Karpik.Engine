### [.NET: ускорение разбора JSON-строк с escape-последовательностями](https://github.com/dotnet/runtime/pull/138016)
- **Что делает / как было:** счётчики при валидации и декодировании теперь хранятся в локальных переменных или вычисляются из индекса; раньше поле ридера и `out`-параметр обновлялись на каждом байте.
- **Польза и цена:** в бенчмарке PR на Linux/Arm64 — **1,62–2,50×** на JSON с HTML; на x64 значимого эффекта не увидели. Кандидат для разбора контента вне тика, не для бинарного RPC. Замер дешёвый, миграция с .NET 10 ради одного патча не оправдана. **Лицензия:** MIT.
- **Этап:** только при необходимости. **Relevance: Medium** — `ContentRegistry` использует `System.Text.Json`, но такой профиль нагрузки у KarpikEngine не подтверждён. **Next step: monitor** — проверить обычные и насыщенные escape-последовательностями документы на Arm64, когда исправление выйдет в поддерживаемой версии.

### [Arch ECS: точное сравнение масок через границу 32-битного слова](https://github.com/genaray/Arch/pull/324)
- **Что делает / как было:** `Exclusive` теперь проверяет и старшие слова второй маски; раньше запрос на точный набор компонентов мог принять архетип с лишним компонентом в следующем 32-битном слове.
- **Польза и цена:** дешёвый регрессионный сценарий для масок Dragon ECS: проверить семантику исключений и лишних старших битов на фактической границе слова. Это проверка корректности, не свидетельство бага в Dragon и не причина менять фильтры в горячем пути. **Лицензия:** Apache-2.0.
- **Этап:** ранний прототип. **Relevance: Medium** — общий класс ошибок в ECS-масках важен для `Shared`, но модели запросов Arch и Dragon не тождественны. **Next step: prototype** — запустить один тест на границе слова для применимого контракта Dragon, без добавления Arch.

### [WebTransport: группа и порядок отправки для двунаправленных потоков](https://github.com/w3c/webtransport/pull/831)
- **Что делает / как было:** редакторский черновик передаёт `sendGroup` и `sendOrder` пишущей стороне исходящего двунаправленного потока; прежний алгоритм терял часть настроек. В приложении приоритеты можно было задавать собственной очередью, но она не управляет планировщиком браузера.
- **Польза и цена:** ориентир для браузерного клиента, если понадобится разделить надёжные команды и передачу контента. Не гарантия задержки и не новая поддержка браузеров. Адаптеры Client/Server и тесты под потерями стоят дороже правки спецификации; протокол `Shared` менять заранее не нужно. **Лицензия:** [W3C Software and Document License](https://github.com/w3c/webtransport/blob/main/LICENSE.md) для текста, BSD-3-Clause для тестов; лицензия реализации проверяется отдельно.
- **Этап:** только при необходимости. **Relevance: Low** — нативный Client/Server уже использует LiteNetLib. **Next step: monitor** — проверять поддержку и p99 очередей только при появлении web-таргета.

## 🏗 Новые движки / нововведения в старых

### [Godot: переимпорт обновляет кэш сцены без активного экземпляра](https://github.com/godotengine/godot/pull/125467)
- **Что делает / как было:** при переимпорте обновляет и `PackedScene`, оставшуюся в памяти без активных экземпляров (например, в истории undo). Раньше переимпорт мог обойти такой ресурс, и следующее создание экземпляра брало старые данные.
- **Польза и цена:** у KarpikEngine уже есть тест первого чтения изменённого слота после commit. Дешёвое дополнение при работе над asset overrides — проверить два последовательных refresh, включая снятие подмены, до первого разрешения ссылки: виден итоговый контент, а неизменившиеся слоты сохраняют поколение. Не нужен обход ECS или перезапуск Lua/Simulation. **Лицензия:** MIT; перенос кода не нужен.
- **Этап:** ранний прототип, вместе с тестами asset overrides. **Relevance: High** — это конкретный сценарий для текущего hot reload, а не подтверждённый дефект KarpikEngine. **Next step: prototype** — добавить регрессионный сценарий при реализации refresh.

### [Stride: отдельные слои света для каждой камеры](https://github.com/stride3d/stride/pull/4046)
- **Что делает / как было:** камера фильтрует источники по битовой маске до подготовки освещения и теней. Раньше виды в одном композиторе делили источники; для независимого превью требовалось разделять сцены или проходы. Маска действует на вид, не на объекты и не на light probes.
- **Польза и цена:** независимый свет для превью и основной сцены — новая возможность Client, не оптимизация текущего 2D-рендера. Фильтр по плотному списку не требует аллокаций; основная цена — поддержка нескольких видов и тесты теней. **Лицензия:** MIT.
- **Этап:** продвинутый этап. **Relevance: Low** — выгода появится только в 3D-пайплайне с несколькими видами. **Next step: ignore** до появления такого требования.

### [Bevy: защита PBR от NaN, попадающих в bloom](https://github.com/bevyengine/bevy/pull/26473)
- **Что делает / как было:** заменяет `pow(x, 5.0)` в приближении Шлика на явные умножения и ограничивает диапазон аргументов в других чувствительных формулах. Раньше округление могло дать отрицательное основание и породить NaN; вспышки подтверждены в веб-сборке, остальные случаи теоретические.
- **Польза и цена:** при появлении PBR/bloom можно дёшево проверить граничные значения в шейдере и тестовой сцене. Это страховка от артефактов в Client, не измеренный прирост FPS и не задача для Server/Shared. **Лицензия:** MIT или Apache-2.0.
- **Этап:** только при необходимости. **Relevance: Low** — сценарий не относится к текущему 2D-пути. **Next step: ignore** до появления PBR/bloom.
